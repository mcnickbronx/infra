# Почему сделано именно так

Что выбрали, почему и что отклонили — чтобы через полгода не разбираться заново.
Контекст: переезд с ISPManager, несколько VDS, свои команды разработчиков, проекты
в Docker Compose, общий Postgres с базой на проект.

**Главное правило — простота.** Возможность появляется, когда есть настоящий случай,
а не «вдруг пригодится»: каждая — это код, тесты, документация и лишнее «если» в голове.

## Ключевые решения

### Движок на сервере: Ansible как панель

Серверы, настроенные руками, незаметно расходятся. Поэтому сервер настраивает движок
на Ansible — одинаково везде, с проверками и восстановлением с нуля. Цена — нет интерфейса,
всё держится на администраторе. Принято сознательно.

Движок работает, как панель: стоит на самом сервере (`/opt/infra`), настройки сервера —
`/etc/infra/server.yml`, пароли — `secrets.yml` рядом, их создаёт сам движок. В git — только
движок, без серверов и паролей. Причины (октябрь 2026, появилась вторая команда):

- **Команды не видят чужие серверы.** Доступ в git выдаётся на весь репозиторий, а пароль
  vault открывал пароли всех серверов. Теперь доступ к серверу и есть доступ к его настройкам.
- **Пароли не дублируются.** Они и так на сервере (`.env` проектов, `/etc/restic/env`), копия
  в git безопасности не добавляла, зато добавляла пароль vault, его передачу и смену. Снаружи
  нужен только пароль restic — в менеджере паролей.
- **Сервер независим.** Админ команды ведёт его сам, без чужого компьютера и репозитория;
  `apply` показывает изменения и спрашивает, прогон идёт службой и переживает обрыв SSH.
- **Доработка без поломки движка:** значение в `server.yml` → свой файл рядом с файлом движка
  (`pg_hba.d`, `conf.d`, свои правила ufw) → своя ветка движка. Первые два — контракт движка.

Привязки нет: движок только применяет настройки, результат — обычная конфигурация Linux.
Удалить `/opt/infra` — сервер работает дальше, меняется он тогда руками (ADMIN.md, «Если движок
больше не нужен»); с панелью вроде ISPManager так не выйдет — она сама держит службы и настройки.

Цена: на каждом сервере стоит Ansible (~150 МБ), человек на нескольких серверах описан
на каждом (до 10 серверов это дешевле общего списка), нет общего вида всех серверов в одном
файле. История настроек — ночные снимки `/etc`.

Движок — открытый репозиторий на GitHub: в нём нет ни серверов, ни паролей, поэтому прятать
нечего. Сервер ставит его `git clone` без ключей и обновляется по тегам (`infra upgrade`); свои
правки в коде — своя ветка или форк.

Теги подписаны SSH-ключом автора, `infra upgrade` ставит только подписанные ключом из `SIGNERS`
той версии, что уже стоит. Иначе слабым местом всех серверов был бы аккаунт GitHub: кто получил
к нему доступ, выпустил бы версию, и её `install.sh` и плейбук выполнились бы от root при первом
обновлении. Подпись — ключом, который не лежит на GitHub, поэтому доступа к репозиторию мало.
SSH-ключ, а не GPG: он у администратора уже есть, проверке нужен только `ssh-keygen`.
Автовыкладке проектов это не помогает: образ из ghcr.io с compose запускается от root, и там
защита — доступ к аккаунту и репозиторию проекта (двухфакторный вход). Открытая история начинается с v1.7.0: в прежнем закрытом
репозитории осталась старая схема (vault, данные серверов).

### Ubuntu 26.04 на всех серверах

Одна ОС — одинаковое поведение и одна проверка на тестовом сервере. 26.04 — поддержка
до 2031. Новая LTS — новыми серверами и переносом проектов, а не обновлением на месте:
заодно проверяются бэкапы, откат — вернуть DNS. Postgres — из PGDG с версией
в `postgres_version`: мажорная версия базы меняется отдельным решением, не вместе с ОС.

### Всё — проекты

Бэкенд, фронт и статика одинаковы: папка с файлами и `compose.yml`. Поэтому на сервере
только проекты — папка, своя сеть, при необходимости база, участники. Инфраструктура
не знает про конкретные приложения: она даёт базу и общие переменные (`DATABASE_URL`,
`DB_*`, `PG*`), а имена, которые ждёт образ, проект задаёт сам.

### Доступ: файлы или Docker. На сервере — одна команда

Участник (`devs`) работает с файлами своих проектов. Docker — у `docker_users`, и это root
на сервере; мы не делаем вид, что это не так. Граница «без Docker» тоже не крепость: `compose.yml`
и `.env` в `web/` пишет участник, а администратор запускает их от root (`project-compose`, меню,
копия базы в `*_dev`). Поэтому доступ к серверу — только тем, кому доверяют сервер; чужим — git
и pull request. Скрипты от root, которые пишут в `web/` (`project-db-env`, `project-deploy`,
`project-db-copy`), по ссылкам не ходят: подложенная участником ссылка не направит запись root
в чужой файл. Так же автовыкладка (таймер и перевод в Docker без root) читает оттуда `DEPLOY_IMAGE`:
`.env`-ссылку, например на `.env` соседа, root не открывает — ни при чтении `DEPLOY_IMAGE`, ни при записи
(`project-db-env`, `to`). Compose проекта от root (`project-compose`, выкладка) открывает `.env` по имени, как
и `compose.yml`, — это внутри модели выше: compose участника с файлами в `web/` и так запускается от root.
Но имя образа из `.env` root берёт как есть
и скачивает своим входом в реестр — чужое имя, вписанное строкой, тоже, если у проекта не задан `image`
(репозиторий его образа в `server.yml`): с ним образ из другого репозитория — отказ. Промежуточного уровня («compose без root»)
нет — см. «Что рассматривали и отклонили». Автовыкладка из git этого не меняет: её compose
запускается от root, поэтому её участники — тоже `docker_users` («Автовыкладка»).

Изоляция людей друг от друга — это разные серверы, а не код. Команды, которые не должны
видеть друг друга (подрядчики, чужие клиенты), — на разных VDS: сервер дешевле сложной
схемы изоляции.

### Защита от взломанного контейнера

Самый вероятный взлом — через уязвимость приложения. Поэтому:
- **своя сеть на проект** — контейнер не достаёт до соседей мимо Traefik и CrowdSec;
  к базе пускает только из сети своего проекта (`pg_hba`);
- **userns-remap** — root в контейнере на хосте обычный uid 100000; `no-new-privileges`
  для всех контейнеров, `/srv/projects` — `nosuid,nodev`. Цена: `web/` открыт контейнерам
  через ACL для типичных групп (0, 33, 1000). Включён всегда: выключать на работающем
  сервере дорого (данные Docker в другой папке, файлы с uid 100000+);
- **порты Docker по умолчанию на 127.0.0.1** (`daemon.json`): `ports: ["8080:80"]` иначе
  открылся бы в интернет мимо ufw;
- **код в контейнере — только на чтение**, писать — в папки данных (`mkdir` + `chmod 2770`).

### Traefik в сети хоста

Видит контейнеры всех проектов, а проекты друг друга — нет. Порты 80/443 подчиняются ufw,
в логах реальные IP (по ним банит CrowdSec). Docker socket подключён напрямую, без
socket-proxy: прокси на 127.0.0.1 был бы доступен каждому с shell на сервере. Взлом
Traefik по сути даёт root — поэтому свежий образ своей минорной версии ставит еженедельный
`update.yml`, он же сообщает о новой минорной (исправления получает только последняя).

### SSH: белый список IP, только ключи

Снаружи открыты только 80 и 443; SSH — только с IP из `admin_ips` и `people`. IP лежат
рядом с ключами, поэтому ушёл человек — ушли и его адреса. Белый список закрывает то, что
ключи не закрывают: украденный ключ без вашего IP бесполезен, а уязвимость в sshd до входа
(как regreSSHion в 2024) до сервера не доходит. Человеку с меняющимся IP — подсеть его
провайдера в `ips`.

**Ссылка доступа** — для мобильного интернета и поездок, где подсети провайдера нет (у оператора
пулы огромные). Одна секретная ссылка на сервер: открыл, нажал кнопку — SSH открыт текущему IP
на сутки (`access_link_hours`), правило ufw с пометкой `infra-access <до>` убирает таймер. Раньше
её не делали как «публичную страницу с правом менять файрвол»; теперь права разделены: страница
работает без прав и не знает секрета (только sha256), кладёт IP в очередь, правило ставит маленький
скрипт root, заново проверив IP (только публичный). Просмотр страницы ничего не открывает — только
кнопка (POST): мессенджеры сами открывают ссылки ради предпросмотра. Утечка ссылки открывает только
порт: без ключа не войти, открытое видно в Telegram и `infra status`, одновременно — не больше
10 адресов; перевыпуск — новый `access_token`. Цена: IP мобильного оператора общий (CGNAT), и на
сутки порт открыт его соседям — их держат ключи и CrowdSec, поэтому не дольше трёх суток. Ссылка
одна на сервер, а не на человека — так решили ради простоты: передать одну ссылку; кто открыл,
видно по IP. Адрес — `<IP>.sslip.io`: своего домена у сервера нет, а sslip.io отвечает адресом
из имени, и Let's Encrypt выдаёт сертификат.

База — только через SSH-туннель (`PermitOpen 127.0.0.1:5432`): к паролю добавляется ключ,
трафик зашифрован, Postgres не виден из интернета.

### Один Postgres на сервер, база на проект

Как в ISPManager, но плейбуком. Память используется лучше, чем Postgres в каждом проекте;
изоляция — правами: `REVOKE CONNECT FROM PUBLIC`, `pg_hba` по подсети проекта, лимит
подключений и времени запроса. Базы в контейнерах проектов не держим: их не забэкапить
консистентно копией файлов.

### Бэкапы: снимок на проект, три уровня, сервер не может стереть копии

Снимок на проект — чтобы восстановить или перенести один проект. Root на сервере есть
не только у администратора, а взломщик первым делом удаляет бэкапы, поэтому правило:
**у сервера нет прав удалять ни одну копию, кроме своей локальной.**

1. **На сервере** — быстрые восстановления после ошибок; при взломе на него не рассчитываем.
2. **У администратора** — `tools/fetch-backups.sh` забирает только новые файлы и ничего
   не удаляет. Файлы restic неизменяемы, поэтому копия сама по себе только дописывается;
   у сервера нет доступа к вашему компьютеру. Слабое место — регулярность.
3. **S3 с Object Lock** (проверено на Timeweb Cloud) — каждую ночь, сервер только дописывает. Блокировка
   держит файл 30 дней с записи, а restic ссылается на старые файлы — поэтому раз
   в 14 дней копия начинается заново в новой папке: свежая полная копия всегда заблокирована.

**Копия прод-базы в dev — только в `*_dev`.** `project-db-copy` заменяет базу целиком: ошибка в порядке
«откуда куда» стёрла бы прод, поэтому «куда» обязано оканчиваться на `_dev` — без обхода. База dev
очищается полностью (а не `pg_restore --clean` поверх): таблицы новых миграций dev иначе остались бы со
старыми данными, и миграции падали бы не из-за кода. Перед заменой — снимок dev, после — миграции кода
dev: ради этого копия и делается. Персональные данные не обезличиваются: dev на том же сервере
и у той же команды, письма из dev не уходят; обезличивание — когда dev уедет к другим людям.
Окно между проверкой ссылок и `install -d`, `rsync`, `chgrp` в `--files` (`roles/backup/files/project-db-copy:105–117`)
проверено опытом на Маке 24.10: 1000 прогонов, пока участник подменяет `media` ссылкой на чужую папку, — захватов
группы чужой папки 0. `install` там — заглушка с поведением uutils 0.10.0 (Ubuntu 26.04) по исходнику, `chgrp` и `find` —
BSD: `chgrp -R` и `install -d -g` меняют группу самой ссылки (`lchown`), `find -type d` ссылку не берёт. На сервере
(ни с uutils, ни с GNU coreutils Ubuntu 24.04) окно не проверялось. Остаток: в узкой гонке (ссылка появилась после
`[ -d ]`, до `install`) `install -d -m 2770 -g <проект>-dev` идёт по ссылке. С uutils — по исходнику ставит цели
режим 2770, группу не меняет: ссылка на `/etc` закрыла бы `/etc` службам не от root. С GNU coreutils (Ubuntu 24.04) —
по исходнику gnulib `mkdir-p.c` и `install.c` меняет и группу цели на `<проект>-dev`: участник получил бы запись в чужую
папку, например `/etc`. Опытом на сервере не проверено; починка — создавать папку без перехода по ссылке.

**Частые снимки — по проекту и сразу в S3.** Ночной снимок — это до суток потерянных данных
(заявки, заказы); проекту, где это дорого, `backup_hourly`: `db` — только база или `all` — база
и папки, раз в `backup_every` минут (по умолчанию 60). Снимки restic добавляют только изменения:
дамп небольшой базы — сотня килобайт, и только если база менялась (рабочий сайт в октябре 2026 — 116 КБ,
до ~30 МБ в сутки при снимке каждые 5 минут). Сразу после снимков — копия в S3 (`restic copy`
дописывает только новое): с потерей сервера теряется не больше `backup_every` минут, а не сутки.
До v1.7 частые снимки уходили в S3 ночью — считали, что каждый час гонять копию тяжело; для
снимка базы в сотню килобайт это не так. Минуты — 1, 5, 15, 30, 60: каждое значение делит
следующее, таймер срабатывает с шагом самого частого проекта, и минута каждого попадает на его
срабатывание (10 и 15 так не сошлись бы). На сервере хранятся 48 часов по одному в час
(`--keep-within-hourly`, не `--keep-hourly`: тот оставил бы 48 последних снимков любого проекта —
полтора месяца ночных), в S3 — все, пока жива папка. С ночным бэкапом — по очереди (одна
блокировка): ночной ждёт частого, частый во время ночного пропускается. Снимок только базы помечен
`db-only`, и восстановление без номера снимка его не берёт: на новом сервере он принёс бы базу без
файлов. Частый `pg_dump` читает всю базу — для базы в гигабайты это нагрузка; чаще минуты и «на
любую секунду» — архив WAL (pgBackRest), это для нагруженной базы отдельно.

Пароль restic и ключи S3 у каждого сервера свои. Перенос проекта идёт через компьютер
администратора: давать серверам доступ друг к другу ради редкой операции не стоит.

### Лимиты: память и CPU на проект, диск — наблюдение

Утечка памяти или майнер не должны класть сервер. Лимит на проект, а не на сервис:
команде не нужно считать память каждого сервиса. Docker так не умеет — контейнеры
проекта кладутся в systemd slice (`cgroup_parent` в `base.yml`). На контейнер — 512
процессов (fork-бомбы) и 65 536 открытых файлов: при умолчании 1024 API на нагрузочном
замере падал с «Too many open files». Квоты на диск на обычном ext4 без переразметки
не сделать — вместо них наблюдение и уведомление.

### Обновления: безопасность — сама, остальное — по команде

Ночью ставятся только обновления безопасности Ubuntu: точечные, ломают редко, медлить
с ними опасно. Всё, что меняет поведение (Docker с перезапуском, Postgres, CrowdSec,
Traefik, ядро с перезагрузкой), — `update.yml` раз в неделю, сначала на тестовом сервере;
он же сообщает о новой минорной версии Traefik. Не запускали больше недели — напоминает
health-check. Мажорная версия Docker закреплена.

### Автовыкладка: сервер сам забирает образ

Push в ветку → CI тестирует и собирает образ с кодом и `compose.yml` в ghcr.io → сервер каждые
15 секунд смотрит, не вышел ли новый, и выкладывает: сервис `deploy` (миграции), запуск с проверкой
здоровья, при сбое — прежняя версия. Сервер забирает сам, а не CI заходит на сервер: наружу
ничего не открывается, белый список IP не мешает, ключей от сервера в GitHub нет, тяжёлая сборка —
не на рабочем сервере. Серверу нужен только токен на чтение образов. Отклонили: вебхук (открытая
точка на сервере и свой код для неё), self-hosted runner (код из репозитория выполнялся бы на
сервере), сборку на сервере (нагрузка на рабочий сервер). Проверка каждые 15 секунд — один запрос к реестру
(около секунды, 0,1 с процессора); в журнал пишутся только выкладки и ошибки.

Автовыкладка даёт root тому, кто управляет образом или папкой проекта: `compose.yml` из образа
(образ выбирает `DEPLOY_IMAGE` в `.env` проекта) запускается от root без проверки, а compose умеет
выйти из userns-remap и смонтировать корень сервера. Поэтому push в выкладываемую ветку — только
тем, кому доверяете root, а участники проекта с автовыкладкой — из `docker_users` (это проверяет
preflight). Проверять compose перед запуском не стали («compose без root» ниже); понадобится
разработчик без root — вернуться к этому.

### Уведомления: Telegram, только изменения и утренняя сводка

healthchecks.io не принимает запросы с российских IP, а свой экземпляр — ещё один сервер.
Поэтому сервер сам пишет в Telegram — бот и чат команды в `secrets.yml`, при закрытом
Telegram — через прокси. Проверки — каждые 10 минут (нагрузку и место ловить вовремя), но
сообщение — только о появившемся и прошедшем: висящая проблема каждые 10 минут приучила бы
не читать. Та же проблема с другими числами — не новая (сравнивается текст без цифр), выросла
до «КРИТИЧНО» — новая. «Прошло» — когда проблемы нет 30 минут: иначе проблема у порога
(нагрузка, перезапуски контейнера) слала бы «новое — прошло» каждые 10 минут. Telegram
недоступен — повтор через час, а не каждые 10 минут. Утренняя сводка напоминает о висящих проблемах и заменяет внешний
контроль «сервер жив»: нет сводки — сервер лежит. Узнать о падении сервера целиком сразу — со
вторым сервером: `watch_sites` — его страницы проверяет тот же health-check, без своей службы и
состояния; «два раза подряд» — повтор через 30 с в одном прогоне (тревога через ≤10 минут, а не 20),
адреса — простым списком, не «сервер → страницы». Отдельного мониторинга (Prometheus, Zabbix)
не ставим: проверки и так в `health-check.sh`, не хватало только доставки. В сводке — число ответов 5xx
по сайтам за сутки из журнала Traefik: только имена роутеров из labels сервера и числа — адреса, страницы
и посетители с сервера не уходят; порогов нет — это число, не тревога. Баны CrowdSec за сутки — так же только
числа по сценариям и только свои баны сервера (`cscli alerts list` без `-a`, без списков сообщества): адреса
в Telegram не уходят.

### CrowdSec вместо Fail2Ban; от DDoS — только HTTP-флуд

CrowdSec получает списки атакующих от сообщества и одинаково закрывает SSH и сайты.
Баны — в файрволе (firewall-bouncer); плагин CrowdSec в Traefik убран: при его сбое
не работали все сайты. На сайтах Traefik ограничивает запросы с одного IP (200 в секунду,
500 одновременных — с запасом на офис за одним NAT). Объёмные атаки на сервере не отразить —
это Cloudflare или защита хостера (с Cloudflare нужен `forwardedHeaders.trustedIPs`).

Своих сценариев нет — только хаб CrowdSec (`http-sensitive-files`, `http-probing`, CVE и т.п.).
До v1.7.1 был свой: запрос к `.env` — бан с первого раза. Убран: один запрос может сделать чужой
браузер — картинка `<img src="https://сайт/.env">` на любой странице, — и все, кто её открыл,
теряли на 4 часа все сайты сервера (бан — в файрволе, на всех портах), а через мобильного
оператора — тысячи людей за одним адресом. Сканер `.env` пробует несколько файлов подряд,
и его ловит общий `http-sensitive-files` (5 разных за несколько секунд). Тот же приём с несколькими
картинками работает против любых HTTP-сценариев — так у CrowdSec везде. Поэтому IP администратора
и участников (белый список SSH) CrowdSec не банит вовсе: свои под такой бан не попадут — ни по логам
сервера (белый список парсера), ни по общему списку сообщества (allowlist `infra`). Нужны оба: парсер
отбрасывает только события из логов этого сервера, а общий список приходит с центрального API мимо
парсеров — до allowlist свой адрес, попавший в него (общий NAT, офис), банился и здесь. Адреса ссылки
доступа — временные и только в ufw: под общий список сообщества они попасть могут (следующий шаг).

Не банит и сам сервер — IPv4 его основного интерфейса (`server_ips`, факты Ansible). Проект без root
ходит к своим доменам не с частного адреса, как общий Docker (частные CrowdSec не банит и так), а с
публичного IP сервера. Боты стучатся на сайт (`/.env`, `/wp-admin`), фронт пересылает адрес в API своего
бэкенда — и CrowdSec видел сканирование с IP сервера и банил его: запросы сервера к своим доменам висели,
фронты отдавали 502 (октябрь 2026, раз-два в сутки). Только IPv4: наружу проект без root (slirp4netns)
ходит только по нему, а IPv6 сервера бывает временным (SLAAC) — запись устарела бы. В список попадает
адрес основного интерфейса: если сервер за 1:1 NAT (на интерфейсе частный адрес) или домены смотрят
на дополнительный IP, это не сработает — нужный адрес добавить своим файлом белого списка CrowdSec
(ADMIN.md, «Что можно менять руками»).

Цена: белый список действует на все сценарии CrowdSec, и на SSH тоже — подбор входа по SSH с IP сервера
(из проекта без root) не банится; риск мал, вход только по ключу. Проект без root, перебирающий сайты
соседей, CrowdSec тоже не остановит — как и проект в общем Docker. И известное ограничение: серверные
запросы фронта без root к своему API идут с одного IP сервера и на роутере API делят лимиты Traefik
(`site-ratelimit`, `site-inflight`, `login-ratelimit`; счётчики — у каждого роутера свои, фронты разных
проектов друг другу не мешают) — под нагрузкой возможны 429. Лечится внутренним
путём фронт → API, мимо Traefik, — отдельная задача.

Журнал запросов Traefik (`access.log`), по которому банит CrowdSec, пишется без имени пользователя из адреса
(`accessLog.fields.names.ClientUsername: drop`). Traefik пишет это имя как есть, а `%0a` в нём — перевод строки:
один запрос `GET http://a%0a<строка журнала>%0ab@<хост>/` от любого анонима, даже на чужой хост,
дописывал в журнал целые строки с любым IP, кодом и роутером (Traefik 3.7.15, октябрь 2026). CrowdSec не отличит
такую строку от настоящей — по ней, вероятно, можно было устроить бан чужого адреса на всех портах (с CrowdSec
не проверяли). basicAuth в infra нет, поле и так всегда было `-`. Путь и заголовки перевода строки в журнал
не дают: `%0a` в пути Traefik пишет как `%0A`, сырые кавычки — ответ 400 без строки. Формат JSON экранировал бы
всё, но меняет то, что разбирает парсер CrowdSec, — правка крупнее ради того же.

### Удаляем только своё

Плейбук удаляет лишнее (ушедших людей, IP, доступ убранных проектов), но только помеченное
как своё — удалить чужое хуже всего:

| Что | Метка «наше» |
|---|---|
| аккаунты людей | группа `devs` (чужой аккаунт с тем же именем — остановка) |
| правила ufw белого списка | комментарий `ansible-wl` |
| роли Postgres проектов | комментарий `ansible-project` (убранный проект — `NOLOGIN`) |
| настроенный Postgres | файл `90-ansible.conf` |

### Проверки: три слоя

Ошибка в инфраструктуре видна только на сервере и часто в редкой операции —
восстановлении, уходе человека; линтеры её не видят. Поэтому: `make check` (шаблоны
сравниваются с эталоном, испорченные описания должны останавливаться), копия движка
на тестовый сервер с повторным прогоном и `verify.yml`, сценарии там же по-настоящему.
Molecule не используем: ufw, systemd, Docker в контейнере ведут себя иначе, чем на VDS.

### Проекты без root — на выбор у проекта (с v1.8.0, экспериментально)

Docker с root — это root для любого, кто пишет `compose.yml` проекта: участника в `web/`, чей проект
запускает администратор, и того, кто делает push в ветку автовыкладки. Когда доступ к серверам и
репозиториям у нескольких человек, ошибка или украденный ноутбук одного — это весь сервер. Поэтому
у проекта можно включить `rootless: true`: свой пользователь `<проект>-run` и свой rootless Docker,
и тогда худшее — это его проект. С автовыкладкой — вместе с `image`: вход в ghcr у root общий, и без ключа
участник вписал бы в `.env` чужой приватный образ. Ключ необязательный: обязательный у проектов без root пришлось бы
дописывать на серверах при обновлении.

- **Docker без root, а не Podman.** Podman легче (нет демона: ~17 МБ на проект против ~100), но через
  совместимый с Docker API (через него работают `docker compose` и движок) в версии 5.7 проверка
  здоровья в форме `[CMD, …]` режется по пробелам — у проектов на web-start выкладка всегда
  откатывалась бы. Вернуться к нему можно, переведя проверки на `CMD-SHELL`: для проектов ничего
  не изменится, меняется только Docker проекта.
- **labels → файл Traefik** (`project-traefik@`): Traefik читает labels только у одного Docker, а свой
  Traefik на проект — это свои 80/443 и сертификаты. Порты контейнеров — на 127.0.0.1, их открывает
  `project-compose`.
- **Postgres по адресу на `infra0`**: localhost хоста контейнерам без root закрыт (иначе им были бы видны
  порты других проектов), своей сети хоста они не видят. Разделяет проекты пароль, а не сеть.
- **`hidepid=2,gid=rootless`**: без видимости `/proc` Docker без root не находит свой systemd и не ставит
  лимиты. Цена — пользователь проекта видит список процессов сервера.
- **Группы (v1.9.0)**: Docker без root — ~120 МБ на каждый; несколько проектов (`rootless: back`) — один
  Docker и один пользователь на группу. Изоляция тогда — между группами, а внутри группы проекты друг
  другу доверяют. Группировать — как удобно команде: по роли (бэкенды, фронты) или по клиенту.
- **Два режима — временно.** Если проекты без root приживутся, в v2.0 общий Docker остаётся только
  для Traefik; если нет — rootless убирается. Третьего режима (Podman рядом) не будет: если он, то
  вместо Docker без root.

## Что рассматривали и отклонили

**Один репозиторий со всеми серверами и vault** (до октября 2026). Не годится для нескольких
команд: доступ в git — на весь репозиторий, пароль vault — ко всем паролям. **Ветка или форк
на команду** — ветки видны всем, у кого есть репозиторий; форки приватного репозитория
на GitHub наследуют его права. **Репозиторий настроек на команду** — изоляция есть, но
настройки и пароли всё равно копия того, что лежит на сервере, и к ней нужен свой ноутбук
с Ansible и vault; держать их на самом сервере проще.

**Проверка compose на сервере («compose без root»).** Была дважды: обёртка `dc`
(до 23.09.2026) и `compose: true` (30.09 — 10.2026, ~700 строк). Проверка и запуск
разнесены во времени (подмена папки ссылкой после проверки), каждая версия compose —
новые ключи, похожие authz-плагины Docker регулярно обходят. Второй раз убрали ещё и потому,
что она защищала единственного участника, с ключом администратора, от него самого.
Если возвращаться (код — в прежнем закрытом репозитории): запускать от root проверенный результат
`docker compose config`, белый список, папки — подпапкой тома (`volume.subpath`), не bind.

**Двухфакторка для SSH (Google Authenticator).** Ломает автоматизацию — Ansible ходит
по SSH, исключение пришлось бы делать для самого ценного аккаунта; мешает SFTP и туннелям
к базе; код на сервере заводится каждому. Второй фактор проще получить ключом, который
нельзя скопировать (Secretive на Mac, YubiKey): сервер такие ключи уже понимает.

**VPN (Tailscale, WireGuard).** Tailscale был опцией и убран: не пользовались, а это роль,
третий режим SSH и зависимость от внешней компании. Для меняющегося IP сделали ссылку
доступа («SSH: белый список IP»); WireGuard — если с меняющихся IP работают постоянно.

**Продление блокировки в S3 каждую ночь** вместо новой папки раз в 14 дней. Места меньше,
но Timeweb эту операцию не документирует, и нужен свой код. **Отдельный сервер
с `rest-server --append-only`** — ещё один сервер; Object Lock — настройка бакета без кода.

**ISPManager, FASTPANEL.** Docker в них — функция администратора без разграничения,
тома не попадают в бэкапы панели.

**Веб-интерфейс к движку.** Движок на сервере — та же панель, но с файлом настроек и командой
`infra` вместо форм. Интерфейс — открытая наружу точка с правами root, свой код с уязвимостями,
вход и права для него; админы и так работают на сервере по SSH. Нужен будет людям без Linux —
вернуться к вопросу (Dokploy, Coolify — «Когда пересмотреть»). Вместо него — меню в терминале
(`sudo infra`, whiptail): вход тот же, что по SSH, новых открытых точек нет, а пункты меню только
вызывают команды движка; своего у меню — смена пароля базы четырьмя шагами из ADMIN.md и строки
в журнал событий (сценарий 6 проходит его клавишами). Восстановления из бэкапа в меню нет: оно
стирает всё, что появилось после снимка, и не отменяется — пусть остаётся командами, где каждый
шаг на виду.
Следующий шаг, если понадобится браузер, — страница в Cockpit поверх тех же команд (вход,
сессии и sudo — его), с паролем и вторым фактором и только с IP админов.

**Dokploy, Coolify.** Удобный деплой из git, но в 2026 году в обеих регулярно находят
уязвимости, дающие обычному участнику root, и приложения живут в общей сети. Возможны
на отдельном сервере одной команды, если ей нужен интерфейс.

**Rootless Docker на проект.** Сначала отклонили (Traefik не видит labels, у каждого демона свои
образы и тома), с v1.8.0 — на выбор у проекта: «Проекты без root» выше.

**Docker Swarm, Kubernetes.** На одном сервере не нужны: Swarm не разграничивает людей,
`docker stack deploy` не понимает `build` и `extends`, а `cgroup_parent` в нём не работает —
пропали бы лимиты. Обновление без простоя даёт плагин `docker rollout` поверх compose.

**Свой почтовый сервер.** Спам-фильтры, блокировки порта 25, SPF/DKIM/DMARC, риск стать
источником спама. Почта — через почту домена или сервис транзакционных писем.

## Убрано ради простоты (октябрь 2026)

Код убранного остался в прежнем закрытом репозитории (открытая история начинается с v1.7.0):
понадобится — спросите в issues.

- **Зеркало пакетов и прокси** (`apt_mirror`, `outbound_proxy`) — были для хостера без выхода
  к зарубежным сайтам; такого сервера нет.
- **MariaDB** — ни один проект её не использовал; нужна только WordPress, его здесь не размещаем.
- **Прямой доступ к базам по IP** (`db_direct`, `db_admin_direct`, TLS) — туннель закрывает
  то же самое с любого адреса.
- **Режимы автообновлений** (`auto_updates: all | manual`) и ночная перезагрузка — использовался один.
- **`docker rollout`** — ни один проект им не пользовался.
- **`host_ports`, `db_test`, `expires`** — сервис для проекта — в его контейнере, тесты — в CI,
  ушёл подрядчик — убрать из `people`.
- **`move-project.yml`** — переезд раз в год-два, проверить плейбук было не на чем; перенос —
  бэкап и восстановление (ADMIN.md, «Восстановление и перенос»).
- **`compose: true`** — см. «Что рассматривали и отклонили».
- **`web-perms`** (раз в минуту возвращал группе запись в `web/`) — вместо него папки данных
  создаются с записью для группы, код в контейнере — только на чтение.
- **Изоляция участников с хоста** (nftables по uid) — на сервере одна команда, а у `docker_users`
  root и так.
- **Напоминания об обновлениях** — health-check считал, сколько дней ждут пакеты, Docker,
  образ Traefik и перезагрузка, ночной таймер следил за версиями Traefik. Много кода ради
  «запусти команду», а висящее напоминание держало проверку упавшей: healthchecks.io пишет
  только при смене состояния и о новой беде не сообщил бы. Теперь `update.yml` раз в неделю.
- **`ssh_access: public`** (SSH всем по ключу) — ни один сервер его не использовал, белый
  список решили оставить; человеку с меняющимся IP — подсеть провайдера в `ips`.
- **Postgres «только если есть проекты с базой»** — он есть на каждом сервере: без условия
  в `site.yml` и признака «настроен нами». Пароль администратора баз обязателен.
- **Middlewares `deny-all` и `hsts-subdomains`** — ни один проект их не использовал.
- **Свой таймер обновления правил CrowdSec** — пакет ставит такой же (`crowdsec-hubupdate`).
- **Vault, инвентарь всех серверов, запуск с ноутбука** — движок на сервере («Движок
  на сервере» выше). Вместе с ними ушли `.env.db` проектов (доступ к базе — в `.env` проекта,
  пароль — в `secrets.yml`) и карточка доступов (`tools/access.sh`): копия себе — сам
  `secrets.yml`.

## Когда пересмотреть

- Команд больше, чем серверов, и придётся селить их вместе → rootless.
- Командам нужен интерфейс → Dokploy на сервере отдельной команды.
- Серверов много и деплой сложный → k3s.
- У людей часто меняются IP → WireGuard.
