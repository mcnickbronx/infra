# Локальное управление серверами

Рабочую копию infra можно использовать как место управления любыми своими серверами.
Общий код движка остаётся в Git, личные сведения — в локальном реестре `.ops`.
Запись сервера в реестре не устанавливает на него infra.

## Тимлиду

В рабочей копии откройте `.ops/README.md` и выберите сервер в таблице. Его карточка
покажет, какие проекты и домены на нём есть, как подключиться и когда проверялись
сервисы и бэкапы.

| Что нужно | Где смотреть |
|---|---|
| Проекты, домены и последнее состояние | Карточка `.ops/servers/<имя>/README.md`. По алиасу или IP сервер можно найти в `.ops/servers.yml`. |
| Настройки и доступы на сервере с infra | `/etc/infra/server.yml`. В `admin_ips` и `people` указаны белые IP и люди, в `projects` — участники, базы, лимиты и автовыкладка. |
| Статус проектов и бэкапов сейчас | `sudo infra status` после входа на сервер с правами администратора. `sudo infra` откроет меню операций. |
| Настройки отдельного приложения | `compose.yml` и `.env` в `/srv/projects/<проект>/web/`. Карточка сервера указывает, где есть локальные копии. |
| Добавить пользователя или проект | [Новый человек](../ADMIN.md#новый-человек) и [Новый проект](../ADMIN.md#новый-проект-сайт). Для изменения конфигурации infra используйте `sudo infra edit`. |
| Что передать разработчику | Личную памятку с адресом, логином, путями проектов и выданными доступами. Общие команды собраны в [TEAM.md](../TEAM.md). |

Для серверов без infra порядок обслуживания указан в их карточках.

## Размещение

Рекомендуемое расположение данных — `~/infra-access/ops`, вне рабочей копии репозитория.
В корне проекта `.ops` — символическая ссылка на эту папку. Так удаление рабочей копии
или `git clean -fdx` может убрать ссылку, но не сам реестр.

```text
infra/
  AGENTS.md                  общие инструкции для ИИ, в Git
  docs/operations.md         устройство реестра, в Git
  .ops -> ~/infra-access/ops  личные данные, вне Git
    README.md                правила работы и карта реестра
    servers.yml              имена, description, доступы и последнее наблюдение
    servers/
      example/               отдельная папка одного сервера
        README.md            описание и команды обслуживания
        .env                 секреты, только когда нужны
        files/               локальные конфиги и материалы восстановления
    templates/server/        заготовка папки сервера и записи в реестре
    journal/                 история работ по месяцам
```

В новом клоне, если приватная папка уже существует:

```bash
ln -s "$HOME/infra-access/ops" .ops
```

Не заменяйте существующую `.ops` вслепую. Если это каталог с данными, сначала сохраните его.
Новый пустой реестр можно начать с папки `~/infra-access/ops` с правами `700`;
файлы реестра и секретов создавайте с правами `600` (`umask 077`).

Правило `/.ops` в `.gitignore` исключает и ссылку, и обычный каталог. Это же правило
читает `tools/rollout.sh` при rsync, поэтому `.git/info/exclude` его не заменяет.
Исключение из Git и раскатки не ограничивает доступ локальных программ к данным.

## Сведения о сервере

`servers.yml` — YAML с `version: 1` и словарём `servers`. У каждой записи есть:

| Поле | Назначение |
|---|---|
| `description` | Понятное назначение сервера; неподтверждённое назначение помечается явно |
| `aliases` | Другие имена, которыми пользователь называет эту же машину |
| `environment` | `production`, `test` или `unknown` |
| `management` | `infra`, `systemd`, `compose`, `panel`, `manual` или `unknown` |
| `management_evidence` | При необходимости источник сведений об управлении: сохранённая конфигурация, дата файла и дата её изучения |
| `ssh` | `target`, `host`, `port`, `user`, путь к ключу и known_hosts; без содержимого ключей |
| `card` | Относительный путь к подробной карточке |
| `secrets` | Ссылки на локальный env и/или серверные файлы; без значений |
| `last_check` | Время с часовым поясом, результат проверки SSH, подтверждённые факты |

`ssh.target` — рабочая цель команды SSH: существующий алиас или `user@host`.
Поля `host`, `port` и `user` фиксируют ожидаемое подключение; перед работой сопоставляйте
их с `ssh -G <target>`. Не меняйте цель автоматически при расхождении.

```yaml
version: 1
servers:
  example:
    description: "Тестовый сервер приложения example"
    aliases: []
    environment: test
    management: unknown
    ssh:
      target: admin@192.0.2.10
      host: 192.0.2.10
      port: 22
      user: admin
      identity_file: ~/.ssh/id_ed25519
      known_hosts_file: ~/.ssh/known_hosts
      strict_host_key_checking: true
    card: servers/example/README.md
    secrets:
      status: not_collected
    last_check:
      checked_at: null
      ssh: not_checked
```

Все новые материалы одного сервера храните в `servers/<имя>/`: описание в `README.md`,
необходимые секреты в `.env`, конфиги и материалы восстановления в `files/`.
Имена снимков должны содержать дату и назначение, например `2026-11-11-before-proxy-change.cfg`.
Копия старой конфигурации может содержать секреты и требует тех же прав, что `.env`.
Общий реестр связывает папки и алиасы, журнал сохраняет историю работ между серверами.

Карточка раскрывает сервисы, зависимости, пути настроек, команды диагностики,
резервные копии, применение и откат. Если что-то неизвестно, это записывается явно.
Инвентарь описывает наблюдения, а не заменяет актуальную конфигурацию на сервере.
Способ управления и доступность — независимые сведения. Таймаут SSH не сбрасывает
известный `management` в `unknown`: сохранённая конфигурация infra или история работ
может устанавливать прежний способ управления. Укажите источник в `management_evidence`,
а ошибку свежей проверки — в `last_check`. Время изменения локального файла не следует
выдавать за дату проверки конфигурации на сервере.

## Доступы и секреты

**Защищайте локальный реестр и его резервные копии.** В `.env`, копиях `secrets.yml`
и архивах могут лежать пароли, токены и ссылки доступа в открытом виде.
Храните каталоги с правами `700`, файлы с правами `600` и шифруйте резервные копии
перед переносом. Права ограничивают доступ других учётных записей. Сжатие в
`.tar.gz` оставляет секреты доступными после распаковки.

На Mac включите FileVault для защиты файлов на заблокированном диске. Программы,
запущенные от вашей учётной записи, могут читать эти файлы, когда диск разблокирован.
[Защита данных с FileVault](https://support.apple.com/en-mt/guide/mac-help/mh11785/27/mac/27).
Для отдельного пароля можно использовать зашифрованный образ диска и извлекать его
после работы. [Зашифрованный образ в Дисковой утилите](https://support.apple.com/en-ie/guide/disk-utility/dskutl11888/mac).

Подключение — обычный OpenSSH. Закрытые ключи остаются в `~/.ssh` или агенте.
Проверка известного сервера по ключу без запроса пароля и принятия нового host key:

```bash
ssh -o BatchMode=yes -o PreferredAuthentications=publickey \
  -o StrictHostKeyChecking=yes -o ConnectTimeout=8 <target> 'id -un; hostname'
```

Если host key неизвестен или изменился, сначала проверьте его по доверенному каналу.
При таймауте фиксируйте таймаут; он не доказывает, что сервер выключен или ключ неверен.

Для нужных операций можно хранить `servers/<имя>/.env`: переменные `NAME=value`,
одна на строку, комментарии отдельными строками, без shell-команд и подстановок.
Парсер должен читать этот файл как данные, а не выполнять `source`/`eval`.
Пустая переменная — незаполненное значение, а не отсутствие пароля на сервере.
Не выводите секреты в чат, журнал и аргументы процессов.

Настройки infra остаются в `/etc/infra` на конкретном сервере. Существующие копии
доступов и материалы восстановления можно перечислить ссылками без переноса содержимого.
Перед переносом старого файла проверьте, не используют ли его SSH-конфиг или другие инструменты.
Приватному реестру нужна отдельная зашифрованная резервная копия. Из Git восстанавливаются
общие инструкции.

## Работа через ИИ

`AGENTS.md` направляет агента к реестру перед задачей на сервере. Это проектная инструкция;
механизм загрузки описан в [OpenAI Docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
В уже открытой сессии при необходимости явно укажите прочитать `AGENTS.md`.

Обычный порядок: найти сервер → проверить текущий доступ и состояние → выполнить поручение
его штатными инструментами → проверить результат → обновить реестр и журнал.
Журнал содержит дату, цель, выполненные изменения, результат проверки и способ отката;
пароли, токены и ссылки доступа в журнал не записываются.

Список сервисов со статусом running не подтверждает работу приложения для клиента.
Проверка SSH не подтверждает здоровье всех приложений и резервных копий.
