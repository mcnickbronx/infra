# Шпаргалка администратора

Что править и какие команды выполнять. Всё — **на самом сервере**, по SSH, через `sudo`.
Подробности и объяснения — в `README.md`.

| Где | Что |
|---|---|
| `/opt/infra` | движок: код «панели» нужной версии (не правится руками) |
| `/etc/infra/server.yml` | настройки сервера: проекты, люди, лимиты — **это вы правите** |
| `/etc/infra/secrets.yml` | пароли сервера: создаёт движок; ключи S3 и токен ghcr вписываете вы |
| `sudo infra` | меню: состояние, проекты (сайты, логи, командная строка в контейнере, перезапуск, откат, бэкап, пароль базы), настройки и ключи, обновления и новая версия движка, журналы, диагностика (диск, память и процессор, Postgres), Telegram, баны CrowdSec, перезагрузка — стрелками; над выводом каждого пункта — его команда |
| `sudo infra edit` | править `server.yml`: проверит, покажет, что изменится, и спросит «Применить?» |
| `sudo infra edit secrets` | то же для `secrets.yml` (ключи S3, ghcr, Telegram); что поменялось — только имена ключей |
| `sudo infra status` | сервер одним экраном: проекты, бэкап, уведомления, что не так |
| `sudo infra apply` | применить `server.yml` как есть: покажет, что изменится, и спросит |

Обязательно у вас (вне сервера): закрытый SSH-ключ и **пароль restic** каждого сервера
в менеджере паролей. Больше ничего: настройки и пароли сервера лежат на нём и в его бэкапах.

**Новому админу — по порядку:** эта таблица → «Что можно менять руками» → «Каждый раз, когда
что-то меняете» → «Где смотреть, что происходило». Остальное — рецепты, по мере надобности.

**Если вы привыкли к панели (ispManager и т.п.)** — это она же, только без веб-интерфейса:

| В панели | Здесь |
|---|---|
| установить панель | `/opt/infra/install.sh` и `sudo infra init` («Новый сервер») |
| главная страница панели | `sudo infra` — меню; `sudo infra status` — сервер одним экраном |
| кнопки у сайта: логи, перезапуск, бэкап | `sudo infra` → «Проекты» → проект; восстановление — только командами («Восстановление и перенос») |
| настройки, сайты, пользователи — формы | `sudo infra edit` — файл `/etc/infra/server.yml` |
| кнопка «Сохранить» | сохранить файл — `infra edit` покажет, что изменится, и спросит «Применить?» |
| пароли хранит панель | `/etc/infra/secrets.yml`, их создаёт движок |
| обновить панель | `sudo infra upgrade <версия>` — когда решите сами |
| журнал действий | `/var/log/infra.log` — кто, когда и что |
| поставить что-то своё | можно всё, кроме файлов движка («Что можно менять руками») |

Веб-интерфейса нет сознательно (DECISIONS.md): это открытая точка с правами root и свой код
с уязвимостями — то, от чего ушли вместе с панелью. Меню `sudo infra` — в терминале, вход тот же,
что по SSH. В нём нет ничего, чего нет в командах: каждый пункт — команда из этой шпаргалки
(её видно над выводом), и в журнал событий попадает так же; от меню — ещё запуск, остановка
и перезапуск контейнеров (кто остановил сайт).

## Что можно менять руками, а что — только через движок

Граница одна: **файл движка начинается со строки «Управляется Ansible»** — следующий `apply`
вернёт его как было. Всё остальное на сервере движок не трогает. Не правил ли кто-то файлы
движка, показывает `sudo infra apply --check`: в нём видно, что `apply` вернёт.

Поменять что-то можно тремя способами, от простого к сложному.

**1. Значение в `server.yml`** — любое умолчание движка (`/opt/infra/group_vars/all/main.yml`):
лимиты проектов, лимиты запросов Traefik, версии, уведомления, S3, часовой пояс. Ключ с опечаткой
остановит проверка в начале `apply`.

**2. Свой файл рядом с файлом движка** — движок его подключает, но не пишет:

| Что | Свой файл или способ | Файл движка — не править |
|---|---|---|
| Postgres: настройки | `/etc/postgresql/17/main/conf.d/95-<имя>.conf` — он важнее движкового | `conf.d/90-ansible.conf` |
| Postgres: кто откуда входит | `/etc/postgresql/17/main/pg_hba.d/<имя>.conf`, затем `sudo systemctl reload postgresql`. Добавить доступ можно, закрыть открытый движком — нет: срабатывает первая подходящая строка | `pg_hba.conf` |
| Postgres: пользователи и базы | свои — руками (`CREATE ROLE ...`): движок ведёт только роли проектов (с меткой `ansible-project`) | роли и базы проектов |
| Traefik | свои файлы в `/srv/infra/traefik/dynamic/` (middlewares, роутеры) — Traefik подхватит сам | `traefik.yml`, `compose.yml`, `dynamic/middlewares.yml` |
| Файрвол | свои правила ufw — без комментария `ansible-wl` | правила с `ansible-wl` (белый список SSH) |
| SSH | `/etc/ssh/sshd_config.d/20-<имя>.conf`: добавить настройку — да, переопределить движковую — нет (у sshd побеждает первое значение). Блоков `Match` там не ставить — они «съедают» все общие настройки после себя | `10-hardening.conf`, блок `ANSIBLE DEVS` в `sshd_config` |
| CrowdSec | свои белые списки, коллекции, источники (`cscli ...`, свои файлы) | `acquis.d/traefik.yaml`, `parsers/s02-enrich/ansible-admin-whitelist.yaml` |
| Docker | — | `/etc/docker/daemon.json`, `/srv/infra/compose/base.yml`, сети `proj-*` |
| Бэкапы | — (что входит в бэкап, решает проект: его папка, тома, база) | `/etc/restic/*`, `backup.sh`, `project-backup`, `project-restore` |
| Логи | свои файлы в `/etc/logrotate.d/` | `logrotate.d/infra`, `logrotate.d/traefik` |

**3. Своя ветка движка** — когда нужно поменять саму логику (роль, шаблон, скрипт). Обновления
из `main` приходят в неё только слиянием руками (README, «Как вносить изменения»).

**Свободно — движок этого не касается:** пакеты (`apt`), свои службы и таймеры systemd, cron,
swap, `/etc/sysctl.d`, `/etc/sudoers.d` (кроме `90-admin`), свои пользователи вне группы `devs`,
`/etc/inputrc` и `/etc/gitconfig` вне блоков с меткой `ANSIBLE`.

**Пароли** — `secrets.yml`: ключи S3, ghcr и Telegram вписываете сами в готовые пустые строки;
сменить пароль базы — удалить
его строку и `apply`; пароль restic не менять («Пароли» ниже).

**Только через `server.yml`, не руками** — то, что движок создаёт сам: люди (аккаунты группы
`devs`, их ключи, IP в файрволе), группы `<проект>-dev`, папки проектов и права на них, лимиты
`proj-*.slice`, таймеры автовыкладки, проекты целиком. Ручная правка здесь проживёт до
следующего `apply`. Свои контейнеры вне проектов не ставьте: у них не будет лимитов, своей
сети и бэкапа — сделайте проектом.

Помнить:

- Ручные правки в `/etc` и `/srv/infra` переживают пересборку сервера — они в ночном снимке
  `system`. Пакеты, службы в `/usr/local` и прочее ставятся заново: коротко запишите их
  комментарием в начале `server.yml` — следующий админ увидит, что на сервере сделано руками.
- В журнал событий ручные правки не попадают: их видно только в `sudo journalctl _COMM=sudo`.
- Нужно на всех серверах — это повод внести правку в движок (новой версией), а не повторять
  руками на каждом.

## Каждый раз, когда что-то меняете

```bash
ssh admin@<сервер>
sudo infra edit     # откроет server.yml; сохранили и вышли — покажет изменения и спросит «Применить?»
```

- Пример всех настроек с пояснениями — `/opt/infra/server.yml.example`: нужный блок — оттуда.
- Ошибку в самом YAML (отступ, ключ дважды) `infra edit` не сохранит — предложит поправить.
  Ошибка в настройках останавливает прогон до изменений и говорит, что поправить; дальше
  на выбор: поправить снова, вернуть `server.yml` как был или оставить.
- Редактор — nano; другой — `sudo update-alternatives --config editor`. Можно и без `infra edit`:
  `sudo nano /etc/infra/server.yml`, затем `sudo infra apply`.
- `sudo infra apply --check` — только показать изменения. Так же видно, не правил ли
  кто-то руками файлы движка: `apply` вернёт их как было.
- Только часть — по меткам ролей: `sudo infra apply --tags base,users` (файрвол, SSH, аккаунты людей),
  `--tags project`, `--tags traefik,crowdsec`, `--tags db`. Метки — имена ролей (README, «Роли»).
  Сменились IP (`admin_ips`, `ips` людей) — только полный `apply`: `admin_ips` — в трёх ролях:
  файрвол (base), белый список CrowdSec (crowdsec), `admin-only` Traefik (traefik); `ips` людей —
  в первых двух.
- Прогон идёт службой `infra-apply`: оборвался SSH или нажали Ctrl+C — прогон дойдёт до конца
  и сам запишет итог в журнал событий; его вывод — `sudo journalctl -u infra-apply` (последний —
  `/var/lib/infra/last-run.log`). Два прогона сразу не запустятся.
- Можно и из tmux или screen: защита от блокировки себя проверит IP всех ваших SSH-сессий.
- После `--tags` изменения `server.yml` в журнале событий — со следующим полным `apply`: только
  он применяет описание целиком.
- С компьютера, не заходя: `ssh -t admin@<сервер> sudo infra apply`.

**Что перезапускается:** конфигурация Traefik — сайты недоступны пару секунд; настройки
Postgres — короткий разрыв подключений; `daemon.json` — Docker (контейнеры переживают,
`live-restore`). Контейнеры проектов движок не трогает.

**Как читать итог** (`PLAY RECAP`): `failed=0` — всё хорошо, повторный `apply` должен дать
`changed=0`; `failed=1` — выше строка `[ERROR]: Task failed: …` с причиной, часто с подсказкой
по-русски; та же причина — в `"msg"` строки `fatal:` (у проверки по списку — `failed:`).

## Рецепты

### Новый сервер

1. Заказать VDS с Ubuntu 26.04, при заказе указать ваш SSH-ключ (вход под root).
2. Поставить движок — как панель, под root. Репозиторий открытый: ключи серверу не нужны,
   отсюда же `infra upgrade` потом берёт новые версии. Нет git — сначала `apt-get install -y git`:
   ```bash
   ssh root@<IP>
   git clone -q https://github.com/mcnickbronx/infra.git /opt/infra && cd /opt/infra
   # Самая новая версия с подписью автора (ключ — в SIGNERS); такой нет — команда остановится
   v=$(for t in $(git tag -l 'v*' --sort=-v:refname); do ./infra tag-signed "$t" && echo "$t" && break; done)
   echo "Версия: ${v:?нет версии с подписью автора}" && git checkout -q "refs/tags/$v" && ./install.sh
   ```
   При первой установке ключ берётся из SIGNERS только что скачанного репозитория: версию без
   подписи или с чужой подписью команда пропустит, но от подмены всего репозитория вместе
   с SIGNERS не защитит. Эту защиту для следующих версий даёт `infra upgrade`: его SIGNERS —
   из уже стоящей версии. Пропущенная версия новее — повод разобраться (ниже, «Обновления»).
   Своя ветка или форк движка (ваши правки в коде) — клонировать его вместо этого адреса: команда
   поставит последний тег, подписанный ключом из SIGNERS этого репозитория, а без своих подписанных
   тегов остановится; своя сборка без подписи — вручную (ниже, «Обновления»).
3. `infra init` — четыре вопроса: имя сервера, email для Let's Encrypt, ваши SSH-ключи и IP.
   Ключи и IP он находит сам — те, с которыми вы сейчас зашли, — их остаётся подтвердить.
   Домашний IP часто меняется: тогда впишите подсеть провайдера или несколько адресов.
4. На «Настроить сервер сейчас?» — `y` (или потом `infra apply -y`): сервер настраивается,
   создаются аккаунт `admin` и пароли (первый раз без предпросмотра: на пустом сервере он
   спотыкается о ещё не поставленные Docker и Postgres). Дальше вход — `ssh admin@<IP>`,
   root по SSH больше не пускает (текущая сессия остаётся). Проекты и люди — `sudo infra edit`
   («Новый проект», «Новый человек»).
5. **Пароль restic — в менеджер паролей:** `restic_password` из `/etc/infra/secrets.yml`.
   Первый `apply` напомнит об этом в самом конце вывода (блок `!!!`) и запишет напоминание
   в журнал событий.
6. Перед тем как пускать сайты — «Перед продакшеном» ниже.

### Перед продакшеном

Само проверяется на тестовом сервере (`make test-vds`). Руками — то, что зависит от
внешнего мира:

- [ ] Пароль restic — в менеджере паролей.
- [ ] Актуальный Traefik (`traefik_image`).
- [ ] Сайт получает SSL (домен с A-записью на сервер).
- [ ] Бан CrowdSec работает: `sudo cscli decisions add --ip <IP телефона> --duration 5m` —
      через 10 секунд сайт с телефона не открывается (свой IP не баньте: закроется и SSH).
- [ ] `tools/fetch-backups.sh admin@<сервер>` забирает копию.
- [ ] Уведомления в Telegram настроены, `sudo infra-notify "проверка"` дошло (рецепт ниже).
- [ ] Знаете, где консоль VDS у хостера.

### Новый проект (сайт)

1. `sudo infra edit`, в `projects:` (пустой `projects: {}` — заменить на блок):
   ```yaml
   projects:
     blog:
       net: 14          # следующий свободный номер на этом сервере, потом не менять
       db: postgres     # или убрать строку — без базы
       devs: [anna]
   ```
   Имя проекта — латиницей: это и имя базы, и пользователя базы.
2. Сохранить и на «Применить?» ответить `y`. Пароль базы появится в `secrets.yml`
   как `db_password_blog`.
3. Доступ к базе — в `.env` проекта, когда он появился (шаг 5): `sudo project-db-env blog`
   (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`; dev-проекту, который читает `DEV_DB_*`, —
   `sudo project-db-env blog_dev DEV_`). Пароль на экран не выводится.
4. У регистратора: A-запись домена → IP сервера.
5. Команда заливает код и `compose.yml` (шаблон в `TEAM.md`) в `/srv/projects/blog/web`
   и запускает `docker compose up -d`. SSL выпустится сам.
   Работаете один — `admin` в папку проекта не войдёт: она открыта только группе `blog-dev`.
   Заведите себя в `people` под своим именем (не `admin` и не имя проекта; ключ — тот же, что
   в `admin_keys`; IP можно не писать — `admin_ips` уже открыт) и впишите в `devs:` проекта
   («Новый человек» ниже). Через `sudo` тоже можно, но владельцем будет root: файлы с правами 644
   (`cp`, `tar`) участники смогут только читать, а поменять права сможет только root.
   Без `docker_users` контейнеры запускайте из-под `admin`: `sudo project-compose blog up -d`.

### Новый человек

1. Человек присылает публичный ключ (`~/.ssh/id_ed25519.pub`, создаётся командой
   `ssh-keygen -t ed25519`) и свой IP (2ip.ru).
2. `sudo infra edit`, в `people:` (пустой `people: {}` — заменить на блок):
   ```yaml
   people:
     anna:
       key: "ssh-ed25519 AAAA... anna@laptop"
       ips: [192.0.2.88]  # дом
   ```
   Несколько ключей — `key: |` и по ключу на строку. Человек на нескольких серверах описан
   в `server.yml` каждого. Других полей у человека нет: опечатка (`ip:` вместо `ips:`)
   или неверный адрес остановят `apply` с сообщением.
3. Имя — в `devs:` нужных проектов. Запускать контейнеры — `docker_users:` (это root на
   сервере, только доверенным). Без Docker участник тоже почти root: его `compose.yml` и `.env`
   вы запускаете от root (`project-compose`, меню). Доступ к серверу — только тем, кому доверяете
   сервер; чужим — работа через git и pull request, автовыкладка заберёт сама.
   Имя не должно совпадать с пользователем, который уже есть
   на сервере (`postgres`, `ubuntu`...): движок остановится.
4. Сохранить и применить — целиком, без `--tags`: IP человека не только в файрволе, но и в белом
   списке CrowdSec.

Человеку отдать: как заходить (`TEAM.md`) и, если нужно, доступ к базе его проекта
(адрес, имя, пароль из `secrets.yml`). Новая группа (`docker`) действует со следующего входа.

### Автовыкладка проекта

Push в ветку → CI собирает образ в ghcr.io → сервер сам его выкладывает (TEAM.md, «Автовыкладка»).

1. Один раз на сервере: токен GitHub (classic) только с правом `read:packages` — в
   `/etc/infra/secrets.yml` (`sudo infra edit secrets`):
   ```yaml
   ghcr_user: "<логин на GitHub>"
   ghcr_token: "<токен>"
   ```
2. В `.env` проекта — `DEPLOY_IMAGE=ghcr.io/<владелец>/<образ>:<ветка>`.
3. `autodeploy: true` в блоке проекта в `server.yml`, `sudo infra apply`. Участники проекта —
   только из `docker_users`: compose из образа запускается от root (DECISIONS.md, «Автовыкладка»).
4. Первая выкладка — в течение минуты: `sudo journalctl -u project-deploy@<проект> -f`.

Откат на предыдущую версию: `sudo project-deploy <проект> rollback` (идёт выкладка — откажет,
повторите после неё). Выключить — убрать `autodeploy`.

Перейти на версию: `sudo project-deploy <проект> to <тег>` (у сайтов на web-start тег — полный хеш
коммита; в меню — «Перейти на версию образа»). Тот же образ, что в `DEPLOY_IMAGE`, с другим тегом:
нет его в реестре — отказ, `.env` не тронут; есть — выкладка сразу, затем тег — в `DEPLOY_IMAGE` в `.env`,
«было → стало» — в журнале событий. Сбой выкладки — работает прежняя версия, `.env` прежний.

### Уведомления в Telegram

Сервер сам пишет в Telegram: каждые 10 минут проверяет диски, нагрузку, память, службы,
контейнеры, сертификаты, выкладки и ночной бэкап и сообщает **только что появилось и что
прошло** — не каждые 10 минут одно и то же. Выросло до критичного (диск 90 %, нагрузка
вдвое выше числа CPU) — новое сообщение с «КРИТИЧНО». Каждое утро — сводка: всё в порядке
или список проблем, диски, нагрузка, память, последний бэкап. **Нет утренней сводки — сервер
лежит.**

1. Бот — у [@BotFather](https://t.me/BotFather) в Telegram: `/newbot`, имя — получите токен.
   Бот свой у команды (или у сервера).
2. Куда писать: чат команды — добавьте туда бота; личный чат — откройте бота и нажмите Start.
3. На сервере, `sudo infra edit secrets` — строки уже есть, пустые, заполните:
   ```yaml
   telegram_bot_token: "123456:ABC..."
   telegram_proxy: "socks5h://логин:пароль@203.0.113.5:1080"   # только если Telegram с сервера закрыт
   ```
4. Напишите что-нибудь в чате, затем `sudo infra-notify --find-chat` — покажет id чатов
   (у групп — с минусом). Впишите нужный: `telegram_chat_id: "-1001234567890"`; несколько
   получателей — через запятую: `"123456789,-1001234567890"`.
5. Проверка: `sudo infra-notify "проверка"` — сообщение в чате. `sudo infra apply` напомнит,
   если бот задан, а чата нет. Время сводки и пороги — `notify_summary_time`, `disk_alert_percent`,
   `memory_alert_percent` в `server.yml` (умолчания — `server.yml.example`).

**Telegram не дёргается зря.** Бот или чат не заданы — ни одного запроса. Ничего не
изменилось — ни одного запроса. «Прошло» — когда проблемы нет 30 минут: то появляется, то
пропадает (нагрузка у порога, контейнер в перезапусках) — одно сообщение, а не каждые 10 минут.
Telegram недоступен — следующая попытка через час, накопленное — одним сообщением.

Токен и прокси — только в `secrets.yml` (в аргументах команд и журналах их нет). Что сейчас
не так, без уведомлений: `sudo health-check.sh`.

### Остальное

| Ситуация | Что сделать |
|---|---|
| Сменился IP у человека | `ips` в `people:` → `sudo infra apply` (полный: IP — в файрволе и в белом списке CrowdSec) |
| IP меняется постоянно | подсеть провайдера в `ips` (`203.0.113.0/24`; подсеть — в whois его IP) |
| Вход с мобильного интернета, в поездке | ссылка доступа (ниже) |
| Человек ушёл | убрать из `devs` и `docker_users` и из `people:` → `apply`; сменить пароли баз его проектов (ниже). Был в `docker_users` — сменить пароли всех баз сервера и проверить, что не осталось его контейнеров |
| Обновить сервер (Docker, Postgres, Traefik, ядро) — раз в неделю | `sudo infra update`, сначала на тестовом («Обновления») |
| Проекту мало памяти / CPU | `memory: 4g` / `cpus: 2` в блоке проекта → `sudo infra apply --tags project` |
| Своя строка в `pg_hba`, своя настройка Postgres, свой роутер Traefik | «Что можно менять руками» выше |
| Проекту нужно PostGIS или pgvector | `sudo apt-get install -y postgresql-17-postgis-3` (pgvector — `postgresql-17-pgvector`, расширение `vector`), затем `sudo -u postgres psql -d <проект> -c 'CREATE EXTENSION postgis'` — и в `<проект>_dev`, если он есть. Пакет запишите комментарием в `server.yml`: на новом сервере и при смене версии Postgres его ставят заново, иначе восстановление базы проекта остановится на расширении. Доверенные расширения (`pg_trgm`, `unaccent`…) проект ставит сам миграцией (TEAM.md, «Расширения Postgres») |
| Сайт переводят на CDN | сначала доработать лимиты Traefik (комментарий в `roles/traefik/templates/middlewares.yml.j2`) и проверить на тестовой VDS: иначе все посетители сайта придут с адресов CDN и упрутся в лимит одного IP |
| Сменился ваш IP | `admin_ips` в `server.yml` → `sudo infra apply` (со старого IP, пока пускает; иначе — консоль хостера, ниже). Полный: IP администратора — ещё в белом списке CrowdSec и в `admin-only` Traefik |

### Ссылка доступа: SSH с меняющегося IP

Одна секретная ссылка на сервер. Открыть её с того устройства и сети, откуда будете входить, нажать
«Открыть SSH» — текущему IP SSH открыт на сутки (`access_link_hours`), в Telegram — сообщение.
Войти по-прежнему можно только своим ключом: ссылка открывает лишь порт.

```bash
sudo infra-access link          # ссылка сервера: https://<IP-через-дефисы>.sslip.io/access/<секрет>
sudo infra-access list          # открытые сейчас по ссылке и до какого времени
sudo infra-access close <IP>    # закрыть раньше срока; all — все
```

То же — меню, «Доступ по ссылке». Ссылку передавайте как пароль (менеджер паролей, личное
сообщение). Утекла или человек ушёл — перевыпустить: `sudo infra edit secrets`, удалить строку
`access_token`, затем `sudo infra apply --tags access` и `sudo infra-access link`. Выключить —
`access_link: false` в `server.yml` (открытые по ссылке IP закроются). Свой адрес вместо sslip.io —
`access_link_host: access.example.ru` (A-запись на сервер).

## Пароли (`/etc/infra/secrets.yml`)

Файл читает только root. Пароль restic, администратора Postgres и баз проектов
(`db_password_<проект>`) движок создаёт сам при первом `apply` и дописывает; записанные
не меняет. Вписываете сами — для этого в файле есть пустые строки: `s3_access_key`,
`s3_secret_key` (копия в S3), `ghcr_user`, `ghcr_token` (автовыкладка), `telegram_bot_token`,
`telegram_chat_id`, `telegram_proxy` (уведомления). Пустое — не используется. Стёртую строку
`apply` вернёт пустой; образец с пояснениями — `secrets.yml.example` движка.

Править — `sudo infra edit secrets`: как `infra edit`, сломанный YAML не сохранит, после
сохранения — предпросмотр и «Применить?». Что поменялось, на экране и в журнале событий —
только имена ключей («сменились ghcr_token»), значения туда не попадают.

**Копия себе** — сам файл, пароли в консоль не выводятся:

```bash
ssh admin@<сервер> sudo cat /etc/infra/secrets.yml > ~/infra-access/<сервер>.yml
```

**Сменить пароль базы** (ушёл человек, который его видел) — в меню: `sudo infra` → проект →
«Сменить пароль базы» (все шаги ниже подряд). Руками: удалить строку
`db_password_<проект>` и `sudo infra apply` — движок создаст новый и сменит его в Postgres.
Затем новый пароль — в `.env` проекта: `sudo project-db-env <проект>` и
`sudo project-compose <проект> up -d --force-recreate`. Только эту строку:
без `restic_password` `apply` остановится (ниже).

**Пароль restic не меняют:** им зашифрованы все копии — на сервере, в S3 и у вас. Он должен
быть в менеджере паролей: при потере сервера без него бэкапы не расшифровать. Пропал из
`secrets.yml`, а репозиторий на сервере есть — `apply` останавливается и просит вписать прежний.

## Регулярно

- **Раз в неделю:**
  - `sudo infra update` — сначала на тестовом сервере, потом на остальных: обновления
    Docker, Postgres, Traefik, пакетов и перезагрузка, если нужна. В конце скажет, если вышел
    новый Traefik. Забыли — через неделю напомнит health-check;
  - `tools/fetch-backups.sh admin@<сервер>` (на вашем компьютере) — копия бэкапов к вам
    в `~/backups`.
- **Раз в несколько месяцев** (или перед крупной переделкой движка): тестовый сервер —
  хоть на день — и `make test-vds`: проекты по-настоящему восстанавливаются.
- **По уведомлениям в Telegram:** диск, нагрузка, память, упавшие сервисы, упавшие и нездоровые контейнеры,
  сайты, которые не отвечают с самого сервера (5xx, таймаут; у `back.<домен>` — `/api/health` не 200), сертификаты, неудачная выкладка, ночной бэкап — что делать, написано в самом уведомлении.
  Каждое утро — сводка; нет её — сервер лежит.
- Обновления безопасности ставятся сами каждую ночь.

## Обновления

Раз в неделю — всё, что не ставится само: Docker (containerd, runc), Postgres в пределах
версии, CrowdSec, пакеты, образ Traefik, перезагрузка после нового ядра:

```bash
sudo infra update             # покажет, что обновится, и спросит; --check — только показать
```

Docker и Postgres перезапускаются (контейнеры работают дальше, у Postgres — разрыв
подключений на секунды); если нужна перезагрузка — через минуту после конца прогона,
минута-две простоя.

**Новая версия движка** — `sudo infra upgrade <версия>`: код нужной версии из git, затем `apply`
с предпросмотром. Какие версии новее — меню `sudo infra` → «Новая версия движка»: подписанные,
сверху — новая; оттуда же и обновиться. Что поменялось — CHANGELOG движка. Правили код прямо
в `/opt/infra` — `upgrade` откажется, чтобы правки не пропали молча: им место в ветке движка.
`--check` и ответ «нет» на «Применить?» — только просмотр: движок возвращается на прежнюю версию
(её `install.sh` идёт ещё раз — минута). Так заранее и проверяют, примет ли новая версия настройки
сервера: `sudo infra upgrade <версия> --check`. Новой версии нужен Traefik новее образа на сервере
(свежий образ скачивает только `infra update`) — `apply` и `upgrade` остановятся до правки настроек
Traefik (без `-y` — ещё в предпросмотре) с советом «сначала `sudo infra update`»; сайты работают как прежде.

`upgrade` ставит только версию, подписанную ключом из `/opt/infra/SIGNERS` (файл берётся из версии,
которая уже стоит): новую версию с GitHub выпустить за автора нельзя, даже получив доступ
к репозиторию, — её `install.sh` и плейбук работают от root. Меню неподписанные версии не предлагает,
а только называет: увидели незнакомую — повод разобраться, а не обновляться. Подменённый на GitHub
тег уже скачанной версии git не примет (`would clobber existing tag`), и `upgrade` остановится.
Версия без подписи (своя сборка, версии до v1.7.1) — только вручную, всё на виду:

```bash
sudo git -C /opt/infra checkout -q <версия> && sudo /opt/infra/install.sh && sudo infra apply
```

Крупные версии программ — числа в разделе «Версии» `group_vars/all/main.yml` движка, то есть
приходят с новой версией движка (или одним серверу — тем же ключом в `server.yml`):

- **Traefik, новая минорная** (3–4 раза в год): исправления безопасности получает только
  последняя, `infra update` в конце пишет «Вышел Traefik v3.x». Прочитать migration guide,
  поменять `traefik_image`, `sudo infra apply --tags traefik`;
- **Docker, новая мажорная:** прочитать release notes, поменять `docker_major_version`,
  `apply` и `infra update`;
- **Postgres, новая мажорная:** не только число — базы переносятся в новый кластер
  (`pg_upgrade` или дамп), отдельной задачей с проверкой на тестовом сервере;
- **Ubuntu** — новыми серверами и переносом проектов, не `do-release-upgrade`.

## Восстановление и перенос

Один проект на том же сервере — файлы, тома и база точно как в снимке (лишние файлы
удаляются):

```bash
sudo project-compose shop down
sudo project-restore shop            # последний полный снимок; другой: project-restore shop /etc/restic/env <id>
sudo project-compose shop up -d
```

**Копия прод-базы в dev** — проверить миграции и код на настоящих данных. Только в проект `*_dev`
(перепутать «откуда» и «куда» и стереть прод нельзя). Меню: проект `*_dev` → «Заменить базу копией
другого проекта» или командой:

```bash
sudo project-db-copy shop shop_dev            # только база
sudo project-db-copy --files shop shop_dev    # и папки media/, private/
```

Перед заменой — снимок dev (номер — в выводе и журнале событий): вернуть как было —
`project-restore shop_dev /etc/restic/env <номер>`. Прод не останавливается. Dev на время
копии останавливается, его база очищается целиком и заменяется копией, затем — миграции кода dev
(сервис `deploy`) и запуск. Не прошла миграция — увидите здесь, а не при выкладке на прод. Данные —
как есть, с персональными: письма из dev уходить не должны (в Django у dev — `EMAIL_BACKEND` console).

**Базу — к себе** (одной командой, прод не останавливается):

```bash
ssh <сервер> sudo project-db-dump shop > shop.pgdump
pg_restore --no-owner --no-acl -d <локальная база> shop.pgdump     # у себя, pg_restore 17+
```

Участнику без sudo — SSH-туннель и пароль базы из `.env` проекта (TEAM.md, «База данных»). В дампе —
персональные данные прода: у себя держите на зашифрованном диске.

**Частые снимки** (`backup_hourly` у проекта в `server.yml`): `all` — база и папки, как ночной
снимок; `db` — только база. Как часто — `backup_every`: 1, 5, 15, 30 или 60 минут (по умолчанию 60,
в :05 каждого часа). Каждый снимок сразу копируется в S3; на сервере хранятся 48 часов, по одному
в час. Вернуть базу на N минут назад, не трогая файлы проекта, — снимок только базы по номеру:

```bash
sudo -i
set -a; . /etc/restic/env; set +a
restic snapshots --tag project:shop,db-only     # снимки только базы: номер, время
project-compose shop down
project-restore shop /etc/restic/env <номер>    # «только база: папки проекта не меняются»
project-compose shop up -d
```

Без номера `project-restore` снимки только базы не выбирает (на новом сервере такой принёс бы
базу без файлов) и говорит, если среди них есть снимок новее выбранного.

Снимки, снимок вручную (то же — меню, проект → «Бэкап сейчас»), отдельный файл или база (от root):

```bash
sudo -i
set -a; . /etc/restic/env; set +a
restic snapshots --tag project:shop
project-backup shop
restic restore latest --tag project:shop --target /tmp/restore --include /srv/projects/shop/web
restic restore latest --tag project:shop --target /tmp/restore --include /var/backups/db
runuser -u postgres -- pg_restore -d shop --clean --if-exists < /tmp/restore/var/backups/db/shop/shop.pgdump
```

**Сервер потерян** — новый сервер с настройками и паролями старого, из снимка старого (тег
`system`, в нём `/etc`), затем проекты. Настройки и пароли — **до первого `apply`**: иначе
движок создаст новые пароли, и ночной бэкап заведёт репозиторий не с тем паролем restic.
Те же пароли баз — и `.env` проектов подходят как есть.

```bash
# 1. Новый VDS и движок — шаги 1–2 «Нового сервера» (без шагов 3–4)
# 2. Репозиторий старого сервера — с вашего компьютера:
rsync -a ~/backups/vds-old/ root@vds-new:/var/tmp/old-repo/
# 3. На новом сервере, от root. restic движок ещё не поставил:
apt-get install -y restic && install -d -m 0700 /etc/restic
#   /etc/restic/old-env (0600): RESTIC_REPOSITORY=/var/tmp/old-repo
#                               RESTIC_PASSWORD=<пароль restic старого сервера из менеджера паролей>
#   из S3: RESTIC_REPOSITORY=<база S3>/vds-old/<самая поздняя дата> и AWS_* ключи
set -a; . /etc/restic/old-env; set +a
restic restore latest --tag system --target /tmp/old --include /etc/infra
cp /tmp/old/etc/infra/server.yml /tmp/old/etc/infra/secrets.yml /etc/infra/
#   в server.yml — то, что у нового сервера другое (admin_ips, если вы теперь с другого IP)
infra apply -y
project-restore shop /etc/restic/old-env
```

**Перенос проекта** — бэкап на старом сервере и восстановление на новом, через ваш компьютер:

```bash
# 1. Блок проекта — в server.yml нового сервера, на нём: sudo infra apply
# 2. Остановить на старом и сделать свежий снимок
ssh admin@vds-old 'sudo project-compose shop down && sudo project-backup shop'
# 3. Репозиторий — к себе и на новый сервер
tools/fetch-backups.sh admin@vds-old ~/backups/vds-old
rsync -a --rsync-path="sudo rsync" ~/backups/vds-old/ admin@vds-new:/var/tmp/old-repo/
# 4. На новом: /etc/restic/old-env, как выше, затем
sudo project-restore shop /etc/restic/old-env && sudo project-compose shop up -d
# 5. Проверить по IP, переключить DNS, убрать проект из server.yml старого сервера
```

На новом сервере у базы проекта другой пароль (`secrets.yml` нового сервера), а при другом
`net` — и адрес: поправьте `.env` проекта. Не получилось до переключения DNS —
`sudo project-compose shop up -d` на старом сервере.

## Где смотреть, что происходило

**Что сейчас — `sudo infra status`**: сервер одним экраном — версия движка, последний `apply`
и применён ли `server.yml`, бэкап, обновления, уведомления, проекты (контейнеры, сайты,
автовыкладка) и что не так прямо сейчас (health-check). С компьютера: `ssh admin@<сервер> sudo infra status`.

**Что было — журнал событий** `/var/log/infra.log`: по строке на событие — когда, кто
(пользователь и IP, «система» — таймер) и что.

```bash
sudo less /var/log/infra.log            # всё по порядку
sudo grep 'shop' /var/log/infra.log     # всё про проект shop
```

Что туда пишется:

- `apply` и `update`: начало, итог (готово / ошибка, число изменений);
- `apply` — и что поменяли в `server.yml` с прошлого раза (diff), и какие пароли появились,
  сменились или удалены (только имена, не пароли);
- `infra edit` — что поменяли в `server.yml` (diff) и вернули ли как было; `infra init`;
- `upgrade` движка — с какой версии на какую, и возврат после просмотра;
- ночной бэкап — готово / с ошибками / не выполнен; снимок проекта вручную;
- восстановление проекта — начато, какой снимок, откуда, итог;
- автовыкладка — версия, готово / не удалась на каком шаге; откат вручную;
- `infra run` (проверки и сценарии).

Журнал хранится два года: раз в месяц новый файл (больше 10 МБ — раньше), старые сжаты,
самые старые удаляются — больше 24 файлов не копится. Каждую ночь журнал попадает в бэкап
(снимок `system`): переживёт и сервер.

**Подробности** — в журнале нужной службы:

| Что | Где |
|---|---|
| весь вывод `apply` / `update` | `sudo journalctl -u infra-apply` (время прогона — в журнале событий); последнего — `/var/lib/infra/last-run.log` |
| ночной бэкап | `sudo journalctl -u backup` |
| автовыкладка проекта | `sudo journalctl -u project-deploy@<проект>` |
| проверки сервера (health-check) | `sudo health-check.sh` — что не так сейчас; `sudo journalctl -u health-check` — каждые 10 минут, о новом и прошедшем — в Telegram |
| пакеты: `update` и обновления безопасности | `/var/log/apt/history.log`, `/var/log/unattended-upgrades/` |
| входы по SSH | `sudo journalctl -u ssh` |
| баны CrowdSec | `sudo cscli alerts list`, `sudo cscli decisions list` |
| сайты (запросы) | `/srv/infra/traefik/logs/access.log` |
| медленные запросы Postgres | `/var/log/postgresql/postgresql-17-main.log` |
| контейнеры проекта | `sudo project-compose <проект> logs --tail 100` |

Чего в журнале событий нет: ручных команд в обход движка (правка файлов, `docker` руками) —
их видно только в `sudo journalctl _COMM=sudo` (кто и какую команду через sudo запускал).
Учётка администратора одна на всех (`admin`), поэтому различить людей можно по IP.

## Если движок больше не нужен

Движок только **применяет** настройки. Всё, что он настроил, — обычная конфигурация Linux
и работает без него: службы и таймеры systemd, Docker, Postgres, Traefik, файрвол, CrowdSec,
бэкапы restic, скрипты в `/usr/local/bin` и `/usr/local/sbin`. Ни одна работающая часть сервера
не зависит от `/opt/infra`. Убрать движок:

```bash
sudo rm -rf /opt/infra /usr/local/sbin/infra /var/lib/infra
```

Дальше работают сайты, ночные бэкапы и копия в S3, автовыкладка, health-check и уведомления,
журнал событий, ротация логов, обновления безопасности.

**`/etc/infra` не удалять:** в `secrets.yml` — пароли баз и restic, их читают уведомления
(`infra-notify`) и `project-db-env`.

Что уходит вместе с движком:

- изменения через `server.yml`: новый проект, человек, лимит — руками (пользователь, группы,
  права, роль и `pg_hba` в Postgres, сеть, slice). Зато перезаписывать ручные правки больше некому;
- `infra update`: Docker, Postgres, Traefik — обновлять самим через `apt`; напоминание health-check
  «update не запускали» — после обновления `sudo touch /var/lib/update-last-run`;
- проверки описания и предпросмотр перед изменениями.

Вернуть движок — «Новый сервер», шаги 2–4, с прежними `server.yml` и `secrets.yml`: `apply`
приведёт сервер к описанию.

## Если что-то сломалось

- **Не пускает на сервер** — консоль VDS в панели хостера (root и пароль от хостера):
  `ufw allow from <ваш IP> to any port 22 proto tcp comment ansible-wl`
  (следующий `apply` это правило уберёт — допишите IP в `admin_ips`).
- **Сайт не открывается** — на сервере:
  `sudo project-compose <проект> ps` и `sudo project-compose <проект> logs --tail 50`
- **Восстановить проект из бэкапа** — «Восстановление и перенос» выше.
- **Сервер в порядке?** — `sudo infra run tests/verify.yml` (только чтение).
- **`infra update` падает на `grub-pc`** («You must correct your GRUB install devices»): в образе
  хостера загрузчик указывает на чужой диск. На сервере `grub-probe -t disk /boot` — настоящий
  диск, затем `echo 'grub-pc grub-pc/install_devices multiselect <диск>' | sudo debconf-set-selections`,
  `sudo DEBIAN_FRONTEND=noninteractive dpkg --configure -a` и `infra update` ещё раз.
