# Изменения движка

Версия движка — git-тег `vX.Y.Z`, на сервер ставится `sudo infra upgrade vX.Y.Z`.
Мажорная версия (`X`) — когда меняется то, на что опираются серверы: ключи `server.yml`,
`secrets.yml` или точки расширения (`pg_hba.d` и т.п.); к ней — инструкция, что сделать
на сервере.

Открытая история репозитория начинается с v1.7.0; записи о прежних версиях — для серверов,
которые обновляются с них.

## Не выпущено

- **Проверка на GitHub — на Python 3.14, как на рабочих серверах (Ubuntu 26.04)**, а не на 3.12; действия
  `checkout` и `setup-python` — v7 на Node 24 (по-прежнему по хешу коммита): GitHub отключает у действий Node 20.
- **`ansible.cfg`: `callback_result_format = yaml` вместо неверного `result_format`** — его Ansible молча пропускал,
  и ошибки прогона шли одной длинной строкой JSON. Теперь — YAML, как и задумано: под строкой `fatal:` или `failed:`
  поля по одному, причина — в `msg:` (длинная — с переносом); строка `[ERROR]: Task failed: …` — как была. `make check`
  проверяет настройки Ansible (`ansible-config validate -t all`): опечатка в ключе — красный; у ошибки шаблона
  показывает и строку `failed:` с `item=` — какой шаблон (в YAML она отдельно от `msg:`).
- **`infra apply` напоминает: `watch_sites` задан, а Telegram — нет.** Сервер следит за страницами другого,
  а «Сайты другого сервера не отвечают» в Telegram не придёт: нет `telegram_bot_token` в `secrets.yml`.
  Напоминание в выводе `apply`, не ошибка — как «бот задан, а чата нет».
- **`tools/rollout.sh <тестовый> --upgrade vX.Y.Z [--from vA.B.C]` — новая версия движка сначала на тестовом
  сервере тем же `infra upgrade`, что на рабочих.** Раньше тестовый получал только копию с компьютера, и `upgrade`
  (подпись по SIGNERS прежней версии, `install.sh`, предпросмотр, проверка сервера) каждый выпуск впервые шёл
  на рабочем. Теперь движок тестового становится git на прежней версии (`--from`, по умолчанию — тег перед новой),
  с GitHub, как у рабочих, затем `apply`, `upgrade` и повтор `apply` без изменений; копия с компьютера не едет —
  прежняя ставится от root, поэтому её тег должен быть подписан ключом из SIGNERS (проверка на компьютере, тот же
  `infra tag-signed`), а тег с GitHub — указывать на тот же коммит, иначе отказ до `install.sh`;
  новая версия уже должна быть на GitHub. Только на сервере с `test_server: true` — иначе отказ до любой
  команды: режим ставит движок на прежнюю версию. Обычная раскатка на тестовом убирает `.git` — движок снова
  копия. `tools/release.sh` называет этот шаг после `git push`.
- **Утренняя сводка: баны CrowdSec за сутки.** Строка «Баны CrowdSec за сутки: 108 адресов — http-probing 67,
  http-sensitive-files 53, …» — сколько разных адресов забанил сам сервер, всего и по сценариям (четыре самых частых;
  `http-crawl-non_statics` — пятым, если был): видно, сколько и за что банят и набирают ли порог посетители кабинетов.
  Только свои баны сервера (`cscli alerts list` без `-a` — без списков сообщества), simulated и captcha не в счёт,
  ручной бан — «другие». Адресов в Telegram нет — только числа (кого именно — `sudo cscli alerts list`); банов нет —
  «нет»; нет `cscli` или он не ответил за 20 с — строки нет. Ключей `server.yml` нет.

## v2.0.0 — 2026-10-24 — сервер следит за сервером, свои DNS, образ проекта в server.yml, история нагрузки, сообщение о выкладке, ошибки сайтов в сводке, заплатки root и журнала Traefik, allowlist CrowdSec

- **Журнал запросов Traefik — без имени пользователя из адреса.** Traefik писал его как есть, с раскодированным
  `%0a`: один запрос `GET http://a%0a<строка журнала>%0ab@<хост>/` от любого анонима (даже на чужой хост)
  дописывал в `access.log` целые строки с любым IP, кодом и роутером. По этому журналу банит CrowdSec —
  вероятно, так можно было устроить бан чужого адреса на всех портах, SSH тоже (с CrowdSec не проверяли). Теперь
  поле не пишется (`accessLog.fields.names.ClientUsername: drop`), на его месте `-` — как и было у обычных
  запросов: basicAuth в infra нет. При `apply` Traefik перезапустится — сайты сервера недоступны несколько секунд.
- **`apply` и `upgrade` останавливаются, если образ Traefik на сервере старше нужного настройкам.** Свежий образ
  скачивает только `infra update`, а со старым Traefik не принимает новую опцию и не стартует — сайты сервера
  не открылись бы. Теперь роль traefik до правки настроек читает версию образа (`docker image inspect`, ярлык
  `org.opencontainers.image.version`) и, если она ниже v3.7.12 (`aliasHeadersStrategy`) или неизвестна,
  останавливается с советом «сначала `sudo infra update`» — без `-y` ещё в предпросмотре; образа нет (новый
  сервер) — проверять нечего. Раньше защитой был только абзац в CHANGELOG v1.10.0.
- **health-check: бэкенд сайта — по `back.<домен>/api/health`.** У доменов `back.*` (бэкенд сайта web-start)
  проверка сайтов открывает не `/`, а `/api/health`, и сбой — любой ответ, кроме 200: раньше бэкенд, который
  на всё отвечает 404 или 400 (чужой маршрут, не тот хост), считался живым — `/` у него и так 404. Тревога —
  та же «Сайты не отвечают», в подробностях — `back.<домен>/api/health — 404`. Домен `back.*` без `/api/health`
  после обновления даст одно уведомление — заранее видно в `sudo health-check.sh`.
- **Журнал событий снова пишет смену паролей.** Отпечатки паролей сортировались в локали того, кто запустил
  `infra`, а сравнивались в локали службы `infra-apply`; при расхождении (у администратора `en_US.UTF-8`
  или `ru_RU.UTF-8`, у службы `C`, в именах `_`) строки «пароли (secrets.yml): появились / сменились /
  удалены …» молча пропадали (так с v1.7.0). Теперь сортировка и сравнение — в локали `C`; файл отпечатков,
  записанный прежней версией, читается верно, пересоздавать его не нужно.
- **`project-deploy <проект> to <тег>` — перейти на версию образа одной командой.** Раньше — копия `.env`,
  `sed` с полным хешем в `DEPLOY_IMAGE` и журнал; опечатка в хеше ломала автовыкладку молча. Теперь тот же образ
  с другим тегом сначала скачивается: нет его в реестре — отказ, `.env` не тронут. Есть — выкладка сразу,
  с тем же возвратом при сбое, и только после неё тег — в `DEPLOY_IMAGE` (новый `.env` — в папке проекта, см. ниже, и одним `mv`,
  владелец и права прежние, `.env`-ссылка — отказ, как у `project-db-env`), «было → стало» — в журнале событий.
  Сбой выкладки — прежняя версия и прежний `.env`. В меню проекта с автовыкладкой — «Перейти на версию образа».
- **`tools/release.sh` — выпуск движка одной командой** (для автора движка): `tools/release.sh X.Y.Z "заголовок"`
  проверяет ветку, чистое дерево, номер версии и записи в «Не выпущено», гоняет `make check`, переносит записи
  под заголовок версии (пустой «Не выпущено» остаётся сверху), делает коммит и подписанный тег и проверяет подпись
  по `SIGNERS`; push — руками (README, «Как вносить изменения»). Серверов не касается: `install.sh` и `infra`
  его не вызывают.
- **Временный `.env` — в папке проекта, куда пишет только root (`project-db-env`, `project-deploy … to`).** Раньше он
  создавался в `web/`, открытой участникам на запись: подменив его ссылкой, участник проекта заставлял root записать
  файл и поставить владельца и права `.env` любому файлу сервера (`project-db-env` — уже на серверах). Теперь временный
  файл — в `/srv/projects/<проект>/` (в неё пишет только root — скрипты это проверяют: иначе отказ, права вернёт
  `sudo infra apply`), `.env` читается один раз и без перехода по ссылке, владелец, права и ACL — как у прежнего,
  подмена `.env` во время записи — отказ. Уведомление о неудачном ручном `to` не отсылает к журналу службы и не обещает,
  что версия выложится сама; после `to <хеш>` автовыкладка из ветки стоит — вернуться: `to main` (ADMIN.md, TEAM.md, меню).
- **Загрузка дольше минуты больше не обрывается: `readTimeout` входа Traefik — 5 минут.** По умолчанию Traefik даёт
  60 с на чтение всего запроса вместе с телом: загрузка файла дольше минуты обрывалась (ответ 499 или 504),
  а приложение получало обрезанное тело. Теперь 300 с — 100 МБ укладываются при отдаче от 2,7 Мбит/с (TEAM.md,
  «Домен и SSL»). Цена — медленный клиент держит соединение до 5 минут (отдельного таймаута на заголовки у Traefik
  нет). При `apply` Traefik перезапускается — секунды без сайтов.
- **Лимит одновременных запросов с одного IP на роутер — 500 (было 150).** Открытый WebSocket или SSE держит место,
  пока открыта вкладка, скачивание — пока идёт: офис за одним адресом с WebSocket на вкладку упирался бы в 150 и получал
  429 на всё, что идёт через этот роутер; двое, открывшие разом страницу со 100 файлами по HTTP/2, — 50 отказов
  (опыт на Traefik v3.7.15 с настройками движка). 500 — офис из 50 человек: ~100 WebSocket и три такие страницы
  разом. Счётчики `site-inflight` и `site-ratelimit`, как у `login-ratelimit`, — у каждого роутера свои: до 500
  на каждом роутере (сайте) с одного адреса; цена — ~110–150 КБ памяти Traefik на соединение. Сервер со своим
  `traefik_inflight_max` в `server.yml` его и сохраняет. В TEAM.md — что лимиты считаются на роутер и тяжёлые пути
  (загрузки) — своим роутером.
- **`infra upgrade` заканчивается проверкой сервера.** После прогона новой версии (и при «изменений нет») `upgrade`
  сам запускает `tests/verify.yml` через `infra run` — только чтение: службы и таймеры, файрвол, SSH, права, аккаунты,
  базы, health-check; весь сервер, даже после `upgrade … --tags`. Не прошла — код 1 и сообщение, а движок остаётся
  новым: сервер уже приведён к нему. `--check`, «нет» и упавший прогон — без проверки. Раньше её запускали руками.
  Действует с обновления *с* этой версии: `upgrade` выполняет код движка, который стоит до него.
- **ADMIN.md: рецепт «Проект с другого сервера (не infra)».** Дамп со своей панели или своих скриптов,
  залитый от `postgres`, оставлял таблицы за `postgres` — приложение получало `permission denied`, сайт — 500.
  Рецепт: дамп `pg_dump -Fc`, недоверенные расширения — заранее, заливка `pg_restore --no-owner --no-acl
  --role=<проект>` (или участником через туннель), проверка владельца, код, `.env` и файлы — участником в `web/`,
  затем `project-db-env` и запуск; Postgres источника — не новее сервера. Ручная заливка из снимка restic помечена «только для дампов движка».
- **Свои DNS сервера — ключом `dns_servers` в `server.yml`** (новый ключ — мажорная версия: откат движка на v1.10.0
  и старше с этим ключом остановит проверка в начале `apply` — «неизвестные ключи ['dns_servers']»; сначала убрать ключ).
  Для серверов, где хостер не пропускает публичные DNS и встают apt, pip и выкладка. Не задан — как раньше, DNS от
  хостера. Список адресов (IPv4 и IPv6; подсеть, строка вместо списка — стоп в начале `apply`) ложится
  в `/etc/systemd/resolved.conf.d/60-infra-dns.conf` до установки пакетов, при правке `systemd-resolved` перезапускается
  (доли секунды без DNS); `systemd-resolved` не работает — стоп с советом; убрали ключ — файл удаляется. `tests/verify.yml`
  проверяет, что имена Let's Encrypt, Docker Hub и Telegram разрешаются и `resolvectl dns` знает эти адреса; health-check
  сообщает «DNS сервера не отвечает», если не разрешается ни одно из трёх (до 15 с на проверку, только когда DNS лежит).
  Контейнеры видят новые DNS после пересоздания (ADMIN.md, «Остальное»).
- **Лимит памяти проекта — жёсткий и на сервере со swap** (`MemorySwapMax=0`): проект, упёршийся в `memory`,
  получает OOM и уведомление, а не уходит в swap. Раньше на сервере со swap ядро сначала вытесняло память проекта
  в swap — сервер мог тормозить, а `Killed process` и уведомления не было. Так у slice каждого проекта и у общего лимита
  группы проектов без root; swap сервера остаётся системе, Postgres и Traefik. Применяет `apply`
  (`daemon-reload`), без перезапуска контейнеров. На сервере без swap ничего не меняется; где swap занят, проект,
  который жил за счёт swap, после обновления начнёт получать OOM — поднимите ему `memory`.
- **Автовыкладка не читает `web/.env` по ссылке.** Таймер `project-deploy` и перевод проекта в Docker без root читают
  `.env` без перехода по ссылке: раньше участник проекта, заменив свой `web/.env` ссылкой на `.env` другого проекта,
  получал его приватный образ — root скачивал его своим входом в ghcr и выкладывал в проект участника. Теперь `.env`-ссылка —
  отказ выкладки («Упавшие сервисы» в health-check), перевод в Docker без root не начинается; FIFO на месте `.env`
  таймер не вешает. Если `web/.env` у вас — ссылка, замените её файлом до обновления.
- **Журнал событий не хранит пароли из `server.yml`.** В diff настроек (`apply`, `infra edit` — и на экране) значения
  ключей с `token`, `password`, `passwd`, `secret`, `api_key`, `private_key` в имени — `***`; ключ и знак `+`/`-`
  остаются — видно, что поменяли. Открытые ключи людей (`key:`) — как есть. Пароли по-прежнему лучше держать
  в `secrets.yml`.
- **История нагрузки за 28 дней — sysstat.** Базовая роль ставит sysstat и включает его снимок раз в 10 минут: после
  ночной тревоги «перегружен» или «мало памяти» утром видно, когда началось и что росло — `sar -q`, `sar -r`, `sar -d -p`
  (ADMIN.md, «Где смотреть»). Хранится 28 дней в `/var/log/sysstat/` (пакет по умолчанию — 7), старше 10 дней — сжато xz.
  В Ubuntu 24.04 пакет ставится с выключенным сбором — `ENABLED="true"` в `/etc/default/sysstat` включает его;
  `HISTORY=28` — в `/etc/sysstat/sysstat`. `tests/verify.yml` проверяет службу, таймер и свежий снимок.
- **Сервер следит за сервером — `watch_sites` в `server.yml`** (новый ключ — мажорная версия, вместе с `dns_servers`:
  откат движка на v1.10.0 и старше с этим ключом остановит проверка в начале `apply` — «неизвестные ключи ['watch_sites']»;
  сначала убрать ключ). Список до 10 страниц другого сервера (`https://shop.example.com/`, `https://back.shop.example.com/api/health`):
  health-check раз в 10 минут открывает их через обычный DNS, как посетитель; 5xx или нет ответа два раза подряд
  (повтор через 30 с) — «Сайты другого сервера не отвечают» в Telegram, ответили — «прошло» через 30 минут, как у всех
  проверок; 2xx–4xx — сервер отвечает. DNS своего сервера не отвечает — не проверяются (тревога о чужом была бы ложной).
  Не задан — как раньше. Задайте на обоих серверах пары — узнаете, что лёг любой, не дожидаясь утренней сводки.
  Адрес — только схема, имя, порт и путь, без пробелов, кавычек, `$`, `` ` ``, `;`; не так, строка вместо списка,
  больше 10, заготовка `example.com` — стоп в начале `apply`.
- **Автовыкладка тянет только образ своего проекта — ключ проекта `image` в `server.yml`** (новый ключ — мажорная версия,
  вместе с `dns_servers`: откат движка на v1.10.0 и старше с этим ключом остановит проверка в начале `apply` — «неизвестные
  ключи ['image']»; сначала убрать ключ). `image: ghcr.io/<владелец>/<образ>` — репозиторий без тега, строчными: автовыкладка,
  `project-deploy … to`, откат и перевод в Docker без root скачивают образ, только если `DEPLOY_IMAGE` в `.env` из этого
  репозитория (тег и дайджест — любые; `shop-evil` или `shop/x` — не `shop`); иначе — отказ «образ не этого проекта»
  до скачивания (видно в «Упавших сервисах»), перевод в Docker без root не начинается. Откат так же сверяет и прежнюю
  версию: чужой образ, выложенный до ключа, не вернёт. compose выкладки получает проверенный образ в окружении
  (`DEPLOY_IMAGE`) — строка вроде `export DEPLOY_IMAGE=<чужой>` в `.env` его не подменит. Нет ключа — как раньше. Проекту
  без root с автовыкладкой — задайте: вход в ghcr у root общий, и без ключа участник мог вписать в `.env` чужой приватный
  образ. Роль project кладёт ключ в `/var/lib/project-deploy/<проект>.image` (пишет только root), убрали ключ — файл удаляется.
- **После push — строка в Telegram: «🚀 <сервер>: <проект> — выложена новая версия, коммит 1a2b3c4».** Шлёт таймер
  автовыкладки, только при удаче и один раз на версию; коммит — из ярлыка образа `org.opencontainers.image.revision`
  (CI web-start ставит его бэкенду), нет ярлыка или он не похож на хеш — без коммита. В журнале событий у выкладки
  теперь и полный коммит — его можно дать `project-deploy … to`. Telegram недоступен — выкладка ждёт отправку не дольше
  15 с и сообщение не повторяет. `to` и откат — без сообщения (их запускает человек и видит вывод).
- **Автовыкладка не создаёт папки томов по ссылке в `web/`.** `web/` пишут участники; если часть пути тома из
  `compose.yml` — ссылка (например, `web/a` — ссылка на чужую папку, а том — `./a/b`), прежний `install -d`
  шёл по ней и создавал папку в чужой папке от root. Теперь `project-deploy` создаёт путь тома по одной части от
  `web/`: любая часть — ссылка (или не папка) → выкладка останавливается с сообщением, которое называет путь
  (как при прочих ошибках подготовки). Режим новой папки ставится на саму папку после входа в неё (подменить её
  ссылкой между созданием и `chmod` нельзя) и явно `02770`. Уже существующие папки тома — и ссылки на существующие —
  не трогаются, как прежде; отказ — только когда папку пришлось бы создавать по ссылке.
- **Утренняя сводка: ошибки сайтов за сутки.** Строка «Ошибки сайтов за сутки (5xx): luk-app: 502 — 7; …» по журналу
  запросов Traefik (`access.log` и вчерашний `access.log.1`): сбой части страниц виден утром, даже когда главная
  открывается. До пяти сайтов с наибольшим числом; ошибок нет — «нет»; журнала нет — строки нет. В Telegram — только
  имена роутеров Traefik из labels контейнеров сервера и числа: адреса, пути и посетители не уходят, строка журнала
  с чужим роутером или не в формате Traefik не считается. Число верно, пока посетитель не может дописать в журнал
  свою строку: подделку кода и роутера в пути, кавычки и переводы строки в заголовках счёт не берёт, а целую
  строку закрывает запись выше — журнал Traefik без имени пользователя из адреса. Строки со временем позже «сейчас + 5 минут» не считаются. Порогов нет — это число
  в сводке, не тревога. Ключей `server.yml` нет.
- Сценарии на тестовом сервере проверяют `project-deploy … to <тег>`: тега нет в реестре — `.env` тот же, отказ; есть —
  выкладка, в `.env` заменена одна строка `DEPLOY_IMAGE`, событие в журнале.
- **`project-restore` не идёт поверх запущенного проекта.** Раньше «контейнеры должны быть остановлены» было только
  в шапке скрипта: забыли `down` — `rsync --delete` и очистка базы шли под работающим приложением, а таймер автовыкладки
  при новой версии в реестре запускал `up` и миграции посреди восстановления. Теперь — отказ «остановите:
  `sudo project-compose <проект> down`», ничего не меняется; Docker проекта не ответил — тоже отказ (не узнать, что
  проект остановлен). На время восстановления автовыкладка проекта ждёт: тот же замок, что у `project-deploy`; идущую
  выкладку восстановление ждёт до 30 с, как `rollback` и `to`, потом отказ — повторить.
- **CrowdSec: ваши IP, IP участников и сервера — ещё и в allowlist `infra`.** Общий список атакующих от сообщества
  их больше не банит: раньше белый список парсера защищал только от банов по логам самого сервера, а общий список
  приходит мимо парсеров. Бан, который уже стоит, снимается при `apply`. Список ведёт `crowdsec-sync-allowlist`
  (как `ufw-sync-whitelist`): лишнее из `infra` удаляет, свои allowlist под другим именем не трогает; проверка
  сервера (`tests/verify.yml`) сверяет его с `server.yml`. Адреса ссылки доступа — временные, не входят.
  Ключей `server.yml` нет.

## v1.10.0 — 2026-10-21 — сжатие текста на сайтах, проверка сайтов с сервера, честный upgrade --check

- **`infra upgrade`: `--check` и «нет» больше не оставляют новый движок.** Раньше `/opt/infra` переключался
  на новую версию ещё до предпросмотра и после `--check`, отказа на «Применить?» или упавшего предпросмотра

  в Telegram (одно, и «прошло», когда починили), строка в утренней сводке; `infra status` считает такой
  контейнер неработающим: «контейнеры 2 из 3, нездоровых 1». Давно нездоровые после обновления дадут одно
  уведомление — заранее их видно в `sudo project-compose <проект> ps`: «(unhealthy)» в STATUS.
- **health-check: сайты, которые не отвечают.** Раз в 10 минут сервер открывает `/` каждого домена из labels
  Traefik работающих контейнеров — здоровых и без healthcheck (о нездоровых и упавших есть свои уведомления) —
  с самого себя, через свой IPv4: тот же путь через Traefik и проект (TLS, роутер, бэкенд), но не через файрвол
  и CrowdSec — бан посетителей эта проверка не видит. Сбой — 5xx или нет ответа за 15 секунд, и через 10 секунд
  снова; редирект, 401–404 — сайт отвечает. Одно уведомление «Сайты не отвечают» со списком доменов (коды —
  в подробностях) и «прошло», когда отвечают. Проверяются первые 30 доменов, по 10 запросов сразу: даже когда
  висят все бэкенды, проверка занимает не больше 100 секунд и не задерживает остальные. Сайт, который уже
  отдаёт 5xx на `/`, после обновления даст одно уведомление — заранее видно в `sudo health-check.sh`.
- **preflight: у людей только `key` и `ips`, адреса — IP или подсеть.** `ip:` вместо `ips:` раньше проходил
  молча и закрывал человеку SSH; адрес вида `198.51.100.300` останавливал прогон ошибкой Python в роли base
  или, при запуске из консоли хостера, уходил в файрвол и CrowdSec. Теперь `apply` останавливается сразу,
  с именем человека и адресом. Правило адреса то же, что у base и `infra init`: IPv4 и IPv6, подсети,
  в том числе с битами хоста (`192.0.2.5/24`), `ips` строкой — как один адрес. Человек без `ips` — как раньше.
- **Traefik: сжатие текста на всех сайтах.** HTML, CSS, JS, JSON, XML, SVG, manifest и RSS от 1 КБ уходят
  сжатыми: br — браузерам, которые его умеют, остальным gzip; первый заход на страницу — в несколько раз меньше
  данных. Картинки, видео и архивы не трогаются, ответ, который проект сжал сам, не пережимается, поток событий
  (`text/event-stream`) идёт как прежде. `apply` перезапустит Traefik — сайты моргнут на секунды.
- Доки: ключ проекта `domains` убран из server.yml.example, START и ADMIN — его никто не читал, домены задают
  labels Traefik. В старых `server.yml` он допустим, как прежде.
- Роли читают факты сервера через `ansible_facts[...]`: `infra apply` и `infra update` больше не печатают
  `[DEPRECATION WARNING]: INJECT_FACTS_AS_VARS…` (ansible-core 2.21), движок готов к ansible-core 2.24, где
  прежние имена уберут. Результат тот же: эталоны `tests/golden` не изменились.

На сервере, перед `sudo infra upgrade v1.10.0`: `sudo infra edit` — у каждого человека в `people`, в том числе у тех,

  (номер — в выводе и журнале): вернуть как было — `project-restore`. Прод не останавливается;
  «куда» останавливается, его база очищается целиком и заполняется копией (от роли «куда»,
  расширения — от postgres), затем миграции его кода (сервис `deploy`) и запуск. `--files` — ещё
  `media/` и `private/`. Пока идёт копия, автовыкладка «куда» ждёт. Без терминала — только с `-y`.
- Меню: у проекта `*_dev` с базой — «Заменить базу копией другого проекта»: откуда, с файлами
  или без, подтверждение.
- `ssh <сервер> sudo project-db-dump <проект> > <проект>.pgdump` — база к себе одной командой
  (pg_dump -Fc, прод не останавливается, в журнал — кто выгрузил).
- **Исправлено: `project-restore` восстанавливал базу неточно** — заменял только то, что есть
  в снимке (`pg_restore --clean`), а таблицы, появившиеся после снимка (например, от миграции, которую
  откатывают), оставались, и следующая миграция падала. Теперь база перед заливкой очищается целиком
  (`project-db-empty`, общий для восстановления и копии), расширения ставятся заново от postgres.

На сервере: `sudo infra upgrade v1.6.0`; в настройках ничего менять не нужно.

## v1.5.0 — 2026-10-09 — ссылка доступа: SSH с меняющегося IP

- **Ссылка доступа** (роль `access`): одна секретная ссылка на сервер,
  `https://<IP-через-дефисы>.sslip.io/access/<секрет>` (свой адрес — `access_link_host`).
  Открыть, нажать «Открыть SSH» — текущему IP открыт SSH на `access_link_hours` (24) часа: правило
  ufw с пометкой `infra-access <до>`, белый список (`ansible-wl`) не трогается. Повторно — продлевает.
  В журнал событий и в Telegram — кому открыт (IP и имя хоста провайдера). По сроку закрывает
  `infra-access-expire.timer` (каждые 5 минут).
- Безопасность: страница (`infra-access-web.service`) работает без прав и знает только sha256
  секрета; правило ставит root (`infra-access process` через `infra-access.path`), заново проверив
  IP — только публичный. Просмотр страницы ничего не открывает (предпросмотр мессенджеров), только
  кнопка. Не больше 10 открытых адресов одновременно, не чаще 10 запросов в минуту с адреса.
- `sudo infra-access link | list | close <IP>|all`; меню — «Доступ по ссылке»; в `infra status` —
  что открыто сейчас.
- Секрет `access_token` создаёт `apply` в `secrets.yml`. Выключить — `access_link: false`.

На сервере: `sudo infra upgrade v1.5.0`, затем `sudo infra-access link` — ссылку сохранить
(менеджер паролей, закладка на телефоне). Сертификат для `<IP>.sslip.io` Traefik получает сам
в первую минуту.

## v1.4.0 — 2026-10-09 — снимки по часам, бан за .env

- **Снимки по часам** — `backup_hourly` у проекта в `server.yml`: `db` — каждый час только база,
  `all` — база и папки проекта, как ночной снимок. На сервере (уровень 1), хранятся 48 часов,
  в S3 уходят с ночным бэкапом. Таймер `backup-hourly.timer` (ровно в :05 каждого часа: 13:05, 14:05…) включён,
  только если такие проекты есть. С ночным бэкапом — по очереди: ночной ждёт часового, часовой
  во время ночного пропускается. Сбой — в health-check (и «давно не было» — больше 3 часов)
  и в `infra status`; в журнал событий — только «перестали получаться» и «снова получаются».
- Снимок только базы — с тегом `db-only`. `project-restore` без номера снимка берёт последний
  **полный** снимок и говорит, если есть снимок только базы новее; с номером такого снимка
  восстанавливает только базу, папки проекта не трогает (ADMIN.md, «Восстановление и перенос»).
  `project-backup --db-only <проект>` — снимок только базы вручную.
- Ночной бэкап хранит ещё и часовые снимки за 48 часов (`--keep-within-hourly 48h`); у проектов
  без `backup_hourly` хранение прежнее.
- CrowdSec: свой сценарий `infra/http-env-file` — запрос к `.env` (`/.env`, `/api/.env.production`…)
  банит с первого раза, на обычный срок (4 часа). Общий сценарий банил после 4 таких запросов.
- Меню: в пункте «Обновления» — предупреждение, что новое ядро перезагрузит сервер (минута-две
  без сайтов), и вопрос перед запуском.

На сервере: `sudo infra upgrade v1.4.0`. Снимки по часам — по желанию: `backup_hourly: db` или
`all` у проекта (`sudo infra edit`).

## v1.3.0 — 2026-10-08 — команды для людей: меню, init, edit, status

- `sudo infra init` — новый сервер по четырём вопросам: имя, email для Let's Encrypt, SSH-ключи
  и IP администратора. Ключи и IP находит сам (authorized_keys, текущая SSH-сессия) —
  их остаётся подтвердить; в конце предлагает сразу `apply -y`. `install.sh` больше не кладёт
  пример в `/etc/infra/server.yml`, а подсказывает `infra init`.
- `sudo infra edit` — правка `server.yml` как `visudo`: в копии; сломанный YAML и ключ,
  повторённый дважды, не сохраняются; после сохранения — что поменялось, предпросмотр
  и «Применить?». Проверка не прошла или не стали применять — поправить снова, вернуть как
  было или оставить. В журнал событий — diff правки.
- `sudo infra edit secrets` — то же для `secrets.yml`; что поменялось, на экране и в журнале —
  только имена ключей, без значений.
- `sudo infra status` — сервер одним экраном: версия движка, последний `apply` и применён ли
  `server.yml`, бэкап (и есть ли копия в S3), обновления, уведомления, проекты (контейнеры,
  сайты, автовыкладка) и что сейчас видит health-check. Только читает.
- `sudo infra` без параметров — меню в терминале (whiptail): состояние, проекты (контейнеры, логи,
  перезапуск и остановка, журнал и откат автовыкладки, бэкап, доступ к базе в `.env`), настройки
  и ключи, `apply`, обновления,
  новая версия движка (список версий с их CHANGELOG), журналы (события, бэкап, health-check,
  последний apply, SSH, sudo), диагностика (что заняло диск; память и процессор проектов против
  лимитов их slice; Postgres — размер баз, подключения против лимитов, медленные запросы приложений),
  Telegram (проверочное сообщение, id чата), баны CrowdSec (список, срабатывания, разбанить IP),
  проверка сервера, перезагрузка. В проекте ещё: сайты (ответ через Traefik сервера, до какого числа
  сертификат, смотрит ли DNS на сервер), командная строка в контейнере, смена пароля базы (новый
  пароль — в Postgres и `.env`, контейнеры пересоздаются). Каждый пункт — команда движка, она
  видна над выводом. Восстановления из бэкапа в меню нет намеренно: оно не отменяется — только
  командами (ADMIN.md). Без терминала `infra` без параметров, как раньше, печатает подсказку.

На сервере: `sudo infra upgrade v1.3.0`; в настройках ничего менять не нужно.

## v1.0.0 — 2026-10-06 — движок на сервере

Ansible работает на самом сервере, как панель; настройки и пароли сервера — на нём самом,
в git только движок (DECISIONS.md, «Движок на сервере»).

- `/opt/infra` — движок и его Ansible (`install.sh`), команда `infra`: `apply` (предпросмотр,
  вопрос, прогон службой `infra-apply`), `update`, `upgrade`, `run`.
- `/etc/infra/server.yml` — настройки сервера: вместо `inventory/host_vars/<сервер>.yml`,
  `people.yml` и раздела «Ваши данные» `main.yml`. Пример — `server.yml.example`.
- `/etc/infra/secrets.yml` — пароли: создаёт роль `secrets`, вместо vault.
- `pg_hba.d/` — свои строки `pg_hba` администратора сервера.
- Журнал событий `/var/log/infra.log` (`infra-log`): `apply` и `update` (кто, итог, diff
  `server.yml`, имена новых и сменённых паролей), `upgrade`, бэкапы, восстановления,
  выкладки и откаты. Хранится два года (24 файла, каждый до 10 МБ), входит в ночной бэкап.
- Логи по кругу: logrotate — каждый час, access-лог Traefik — файлы до 200 МБ.
- Защита от блокировки себя: из tmux и screen проверяются все SSH-сессии пользователя; IP
  не удалось узнать — остановка (раньше проверка пропускалась). Неизвестный ключ верхнего уровня
  в `server.yml` — тоже остановка, как у проектов. Пароль restic не создаётся заново, если
  репозиторий уже есть.
- Убраны: vault и `.vault_pass`, `inventory/`, `.env.db` проектов (доступ к базе — в `.env`
  проекта), карточка доступов `tools/access.sh` (копия себе — `secrets.yml`), запуск
  с ноутбука; `fetch-backups.yml` → `tools/fetch-backups.sh`.

**Переход сервера с прежней схемы** (настроенного `ansible-playbook site.yml` с ноутбука;
первый рабочий сервер переведён так 2026-10-06: предпросмотр — только скрипты и журнал, повторный apply — 0 изменений).
Пароли переносятся как есть — работающие проекты и ваш вход в базы ничего не заметят:

1. Движок — `git clone` и `install.sh` (ADMIN.md, «Новый сервер», шаг 2;
   под `admin` — те же команды через `sudo`).
2. `/etc/infra/server.yml` — из прежних `host_vars/<сервер>.yml`, людей этого сервера
   из `people.yml` и раздела «Ваши данные» `main.yml`, плюс `server_name`.
3. `/etc/infra/secrets.yml` — прежние значения из vault (`ansible-vault view
   inventory/group_vars/all/vault.yml` на ветке `main`):
   - `restic_password` ← `vault_restic.<сервер>.password` — иначе старые копии не прочитать;
   - `postgres_admin_password` ← `vault_postgres_admin_password` — иначе сменится ваш вход в базы;
   - `db_password_<проект>` ← `vault_db_passwords.<проект>`, у каждого проекта с базой — иначе
     `apply` сменит пароль в Postgres, а контейнеры останутся со старым из `.env`;
   - при S3 — `s3_access_key`, `s3_secret_key` ← `vault_restic.<сервер>.access_key`, `.secret_key`;
     при автовыкладке — `ghcr_user`, `ghcr_token` ← `vault_ghcr.user`, `.token`.
4. `sudo infra apply`. Строка «Новые пароли в secrets.yml» в предпросмотре значит, что какой-то
   пароль не перенесён: ответить «нет», дописать, повторить.
5. `.env.db` проектов движок больше не обновляет; пароли в нём прежние и действуют. Удалить его,
   когда его не читает ни один compose: `sudo grep -l env.db /srv/projects/*/web/compose*.y*ml`
   ничего не нашёл — `sudo rm /srv/projects/*/.env.db`. Иначе сначала доступ к базе — в `.env`
   проекта (TEAM.md), перезапуск его контейнеров.
