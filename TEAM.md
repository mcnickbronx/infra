# Инструкция для команд

Короткая памятка: как работать со своими проектами на сервере.

## Вход

```bash
ssh <логин>@<сервер>          # командная строка
sftp <логин>@<сервер>         # или любой SFTP-клиент: FileZilla, WinSCP, IDE
```

Вход только по вашему личному SSH-ключу и только с IP, которые вы сообщили
администратору. Сменился IP (переезд, новый провайдер) — напишите администратору. С мобильного
интернета или в поездке — ссылка доступа сервера (её даёт администратор): открыть с того устройства,
откуда будете входить, нажать «Открыть SSH» — ваш текущий IP пускают на сутки, ключ нужен как обычно.

После входа вы в домашней папке. Удобное на сервере:

```bash
go                     # в папку своего проекта; проектов несколько — go <проект>, Tab дополняет
mc                     # файловый менеджер (Midnight Commander), выход — F10
docker compose l<Tab>  # Tab дополняет команды, опции, сервисы, пути
docker<↑>              # стрелки листают прошлые команды, которые начинаются с набранного
```

## Где что лежит

```
/srv/projects/<проект>/
  web/                    ваши файлы: код, compose.yml, .env — всё здесь
```

Работайте прямо в `/srv/projects/<проект>/web`: в SFTP-клиенте и IDE сохраните этот
путь в закладки. Список проектов в `/srv/projects` не показывается, но в свою папку
зайти можно. Чужие проекты вам не видны. В `web/` можно всё: заливать файлы,
делать `git clone` / `git pull`, править `compose.yml`.

## Как залить код

**Через git:** папка `web/` проекта должна быть пустой перед первым clone.

```bash
ssh -A <логин>@<сервер>                  # -A: ваш SSH-ключ для GitHub/GitLab работает на сервере
cd /srv/projects/shop/web
git clone git@github.com:example/shop.git .
# дальше обновления:
git pull
```

Вместо `-A` можно положить на сервер deploy-ключ репозитория в `~/.ssh/`.

**Через SFTP:** просто залейте файлы в `/srv/projects/<проект>/web`.

## Автовыкладка

Выкладка из git без входа на сервер (включает администратор: `autodeploy: true`). Push в ветку →
CI собирает образ → сервер каждые 15 секунд смотрит, не вышел ли новый, и выкладывает его сам.
Что нужно от проекта (пример — ниже):

- **CI собирает образ** с кодом в `ghcr.io/<владелец>/<образ>:<ветка>`; внутри образа —
  `/deploy/compose.yml`, compose проекта. На сервер его руками не кладут: сервер берёт его из образа;
- **в `.env` проекта** — `DEPLOY_IMAGE=ghcr.io/<владелец>/<образ>:<ветка>`, у сервисов приложения
  в compose — `image: ${DEPLOY_IMAGE}`;
- **сервис `deploy`** (`profiles: [deploy]`) — что сделать перед запуском новой версии: миграции,
  статика. Упал — новая версия не запускается. Нет такого сервиса — шаг пропускается;
- **healthcheck** у сервиса с сайтом: сервер ждёт, пока он станет здоровым;
- папки, которые монтирует compose (`./media`), сервер создаёт сам, с записью для группы.

Самый короткий вариант — образ на каждый push в `main` и `dev` (тесты — отдельным job перед ним,
`needs: test`):

```dockerfile
# Dockerfile — в конце: compose проекта едет внутри образа
COPY compose.yml /deploy/compose.yml
```

```yaml
# .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main, dev]
jobs:
  image:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/<владелец>/<образ>:${{ github.ref_name }}   # имя — строчными буквами
```

Push в эту ветку — это root на сервере: compose из образа запускается от root. Право push в неё —
только у тех, кому администратор доверяет сервер.

Не вышло на любом шаге — работает прежняя версия, эта больше не пробуется: исправьте и сделайте
push. Администратору приходит уведомление. Откат на предыдущую версию — к администратору
(`sudo project-deploy <проект> rollback`) или `git revert` и push.

## Кто запускает контейнеры

Два уровня, их выдаёт администратор:

- **Только файлы** (по умолчанию). Перезапустить контейнеры просите коллегу с Docker или
  администратора. Статике перезапуск после заливки обычно не нужен.
- **Docker** (группа `docker`). Это полный доступ к серверу: все проекты, пароли
  баз, бэкапы. Поэтому он есть не у всех. Ничего не проверяется.

К базе подключайтесь со своего компьютера (см. «База данных»).

## Как запустить: docker compose

Всегда из настоящей папки проекта:

```bash
cd /srv/projects/shop/web
docker compose up -d                  # запустить всё
docker compose up -d --build          # пересобрать образы и перезапустить
docker compose ps                     # статус контейнеров
docker compose logs -f --tail 100 web
docker compose restart worker
docker compose down                   # остановить (данные в volumes сохраняются)
docker compose pull                   # скачать новые версии образов
docker compose exec web bash          # shell ВНУТРИ контейнера
docker compose run --rm web python manage.py migrate
```

Имена в командах — это имена **сервисов** из compose (`web`, `worker`).
Без входа на сервер: `ssh <логин>@<сервер> 'cd /srv/projects/shop/web && docker compose logs -f web'`.

**Не запускайте compose через ссылку или из другой папки.** Compose запоминает пути
к файлам проекта: запуск через ссылку привязывает контейнеры к вашей домашней папке —
когда ваш аккаунт удалят, они перестанут запускаться.

**Правила для compose** (ниже) никто не проверяет: Docker выполнит всё, что написано,
правила соблюдайте сами.

## compose.yml

Лежит в корне `web/`. Четыре обязательные вещи — на примере Django:

```yaml
name: <проект>                       # 1. имя проекта — как папка в /srv/projects

x-app: &app
  extends: { file: /srv/infra/compose/base.yml, service: hardened-strict }   # 3.
  env_file: [.env]                   # секреты проекта и доступ к базе
  deploy: { resources: { limits: { memory: 1g } } }                          # 4.

services:
  web:
    <<: *app
    build: .
    labels:                          # наружу — только через Traefik
      - traefik.enable=true
      - traefik.http.routers.<проект>.rule=Host(`app.example.com`)
      - traefik.http.routers.<проект>.entrypoints=websecure
      - traefik.http.services.<проект>.loadbalancer.server.port=8000

  worker:
    <<: *app
    build: .
    command: celery -A app worker

  redis:                             # без labels — снаружи не виден
    extends: { file: /srv/infra/compose/base.yml, service: hardened }
    image: redis:7-alpine
    deploy: { resources: { limits: { memory: 256m } } }

networks:                            # 2. сеть проекта
  default:
    name: proj-<проект>
    external: true
```

1. **`name: <проект>`** — первой строкой, точно как папка в `/srv/projects/`.
   По этому имени проект получает свои лимиты, а бэкап находит его volumes: с другим
   именем не будет ни лимитов, ни бэкапа volumes. Администратор получит уведомление.
2. **Сеть проекта** — все сервисы попадут в неё, другие проекты её не видят.
3. **`extends`** — общие настройки безопасности, лимиты по умолчанию и время сервера
   (московское) у каждого сервиса:
   `hardened-strict` — для приложений не от root (Python, Node, Go, Java);
   `hardened` — для образов, которые стартуют от root (nginx, apache, php-fpm, redis).
   Не запускается с `hardened-strict` — попробуйте `hardened`; не помогло — к администратору.
4. **Лимиты на проект.** Все сервисы проекта вместе получают по умолчанию 2 ГБ памяти
   и половину CPU сервера — делите между ними как хотите. Проекту мало — к администратору.
   Внутри можно ограничить и отдельный сервис, как `web` в примере
   (`deploy: { resources: { limits: { memory: 1g } } }`), чтобы, например, воркер
   с утечкой не отнял память у сайта. Проект упёрся в память — самый большой процесс
   убивается, сервис перезапускается, администратору приходит уведомление.
   Место на диске не ограничено, поэтому см. «Правила» про логи и данные.

   У каждого контейнера ещё два предела. **512 процессов и потоков** — защита
   от fork-бомб; в него упирается сервер, который заводит поток на каждый запрос
   (Django под ASGI с обычными синхронными view): под нагрузкой — «can't start new thread»
   и ошибки 500. Такие приложения запускайте под WSGI (gunicorn) с фиксированным
   числом потоков. **65 536 открытых файлов** на процесс, а каждое соединение — файл;
   больше в своём compose задавать не нужно.

Root внутри контейнера на сервере — не root (userns-remap). Контейнер видит `web/`,
если процесс работает от группы root, www-data (33) или 1000 — это почти все образы.
Приложение пишет «Permission denied» на свои файлы — задайте сервису `user:` с одной
из этих групп (например, `user: "1000:1000"`) или обратитесь к администратору.
Писать контейнер может только туда, где у группы есть запись: папки для загрузок
создавайте с ней (`mkdir media && chmod 2770 media`). Файлы, залитые по SFTP или git
(обычно 644), контейнер и коллеги только читают. Код, который приложение не должно
менять, монтируйте только на чтение: `volumes: ["./app:/usr/www/app:ro"]`.

Секреты и доступ к базе — в `.env` рядом с `compose.yml`. Если `web/` — это git-репозиторий,
добавьте `.env` в `.gitignore`. Пароли по умолчанию (`${PASSWORD:-admin}`) — убрать.

Режим разработки и локальная база — в `compose.override.yml` (или
`docker-compose.override.yml`) только у вас на компьютере.
На сервер его не заливайте и добавьте в `.gitignore`: `docker compose` подхватывает
его автоматически, и на сервере запустится режим разработки.

## Статический сайт

```yaml
name: <проект>

services:
  site:
    extends: { file: /srv/infra/compose/base.yml, service: hardened }
    image: nginx:stable-alpine
    volumes:
      - ./dist:/usr/share/nginx/html:ro     # сюда заливайте билд
    deploy: { resources: { limits: { memory: 128m } } }
    labels:
      - traefik.enable=true
      - traefik.http.routers.<проект>.rule=Host(`promo.example.com`)
      - traefik.http.routers.<проект>.entrypoints=websecure
      - traefik.http.services.<проект>.loadbalancer.server.port=80

networks:
  default:
    name: proj-<проект>
    external: true
```

Файлы в `dist/` отдаются сразу после заливки, перезапуск не нужен.

## Периодические задачи (cron)

Задачи по расписанию — в compose проекта отдельным сервисом, **не в crontab на сервере**:
crontab человека перестаёт работать, когда его аккаунт удаляют, не попадает в бэкап
проекта и не переезжает вместе с ним. Сервис в compose всё это переживает.

Удобнее всего [supercronic](https://github.com/aptible/supercronic) — cron для
контейнеров, вывод задач идёт в логи Docker. В `Dockerfile` приложения
(свежая версия и sha256 файла — на странице релизов; файл с другой суммой не соберётся):

```dockerfile
ADD --checksum=sha256:a53ae236602c7338aba3fbaff40bda6300eae3b9fedb8261eb06cfe3724430c1 --chmod=755 \
    https://github.com/aptible/supercronic/releases/download/v0.2.49/supercronic-linux-amd64 /usr/local/bin/supercronic
```

Файл `crontab` в репозитории, время — московское (как на сервере):

```
*/5 * * * * python manage.py send_emails
0 3 * * *   python manage.py clearsessions
```

Сервис рядом с `web` — тот же образ, та же база (пример Django выше):

```yaml
  cron:
    <<: *app
    build: .
    command: supercronic /app/crontab     # путь к файлу внутри образа
    stop_grace_period: 1s
```

Логи задач: `docker compose logs -f cron`. Задача, которая не закончилась к следующему запуску,
второй раз не стартует — в логе предупреждение.

`stop_grace_period` — из-за выкладки: при остановке supercronic ждёт идущую задачу, а compose
запускает новые контейнеры, только пересоздав все, — сайт не отвечал бы, пока она идёт (Docker
ждёт до 10 секунд). С ним задача обрывается через секунду, поэтому долгая задача должна спокойно
переносить обрыв и повтор.

- Django с Celery — вместо этого `celery beat`.
- Одна простая задача — можно без supercronic:
  `command: sh -c 'while true; do php cron.php; sleep 300; done'` и рядом `init: true` —
  `sh` первым процессом контейнера сигнал остановки не слушает, и выкладка ждала бы его те же 10 секунд.

Время в контейнерах берётся с сервера через `extends` — `TZ` задавать не нужно.
Если задать `TZ`, а в образе нет пакета `tzdata`, время молча станет UTC.

## Домен и SSL

Сервису, который должен быть доступен снаружи, — labels Traefik (см. примеры выше).
SSL-сертификат, защита CrowdSec и заголовки безопасности подключаются сами.
Домен должен заранее указывать на IP сервера (A-запись).

Traefik один на сервер и отдаёт домен тому контейнеру, в labels которого он указан.
Поэтому в labels — только домены своего проекта, а имена роутеров, сервисов и
middlewares — `<проект>` или `<проект>-что-угодно`: одинаковые имена у двух проектов
ломают оба сайта. Новый домен — скажите администратору.

Общие middlewares: `admin-only@file` — доступ только с IP администратора (служебные
панели: Flower, админки), `login-ratelimit@file` — ограничение частоты запросов
(форма входа).

На всех сайтах действуют лимиты с одного IP: около 200 запросов в секунду и 150
одновременных. Сверх них Traefik отвечает 429. Если приложению нужно больше
(API, который часто опрашивают, нагрузочный тест), напишите администратору.
Нагрузочный тест бэкенда удобнее вести мимо Traefik — с сервера по адресу контейнера
в сети проекта (`172.20.<net>.x`): так в результате виден бэкенд, а не лимиты.

## Правила для compose

Их никто не проверяет — отвечает тот, кто запускает:

- **Без `ports`.** Наружу — только через Traefik. Порт без адреса (`8080:80`) откроется
  только на 127.0.0.1 сервера, а `0.0.0.0:8080:80` — в интернет мимо файрвола;
- `privileged`, `cap_add` (сверх обычных прав), `devices`, `network_mode: host`,
  `pid: host`, `userns_mode`, `security_opt`, `sysctls` (кроме `net.*`) — только
  по согласованию с администратором;
- монтировать — только папки своего проекта (`./...`) и volumes проекта, без ссылок
  на чужие папки. Папку, куда пишет приложение, создайте заранее с записью для группы:
  `mkdir media && chmod 2770 media` (иначе её создаст Docker от root, и приложение
  не сможет писать);
- **Traefik** — только домены проекта, в каждом правиле роутера — `Host(...)`;
  без `traefik.tcp` / `udp`, `forwardAuth`, `server.url`;
- **сборка** — `build: .` (папка проекта); у собранного образа нет `image:` (compose
  назовёт его `<проект>-<сервис>`) или `image: <проект>-...`; без `ssh`, `secrets`,
  `cache_to`, `network: host`. Образы других проектов (`<другой проект>-...`) не брать;
- `secrets` и `configs` — не из файлов: секреты — в `.env`;
- у томов и сетей не задавайте свой `name:` и не берите тома `external: true`: бэкап
  берёт только тома `<проект>_<ключ>`. Том с другим именем в бэкап не попадёт, ночной бэкап
  не удастся, пока его не переименуют, а администратору придёт уведомление;
- тома без имени (`volumes: [/data]` или `VOLUME` в образе) — временные: пропадают при
  `docker compose down` и в бэкап не входят. Данные, которые нужно хранить, — в томе
  с именем (`volumes: [data:/data]` и `data:` в разделе `volumes:`) или в `web/`;
- `extends` у каждого сервиса: без него сервис вне лимитов проекта, без `restart`
  и без защиты — он может занять весь сервер (администратору придёт уведомление);
- **логи — в stdout/stderr,** а не в файлы внутри контейнера: логи Docker ограничены
  по размеру (10 МБ × 5 файлов на контейнер, старое вытесняется), а файлы внутри контейнера
  растут, пока не кончится диск всего сервера. Свои опции `logging:` в compose предел
  не снимают — Docker добавляет его к ним сам;
  Данные (загрузки, кеши) — в volumes или `web/`, чтобы было видно, сколько места занято;
- своя база в контейнере — нельзя: её не будет в нормальных бэкапах;
- сеть `proj-<проект>`: без неё контейнеры не достучатся до базы.

## База данных

- Доступ к базе даёт администратор: адрес **`172.20.<net>.1`** (номер сети проекта),
  порт 5432, база и пользователь — имя проекта, пароль. Его кладёт в `.env` проекта команда
  `sudo project-db-env <проект>` — строки `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`,
  `DB_PASSWORD` (с `DEV_` вторым параметром — `DEV_DB_*`). Приложение ждёт другие имена
  (`DATABASE_URL`...) — переименуйте у себя. Сменил администратор пароль базы — та же команда
  и пересоздать контейнеры, иначе приложение не подключится.
- Со своего компьютера (DBeaver, DataGrip) — через SSH-туннель: порт базы снаружи закрыт.
  В DBeaver: на вкладке **SSH** включить «Use SSH Tunnel», хост — IP сервера, ваш логин,
  ключ; на основной вкладке хост **`127.0.0.1`** (не `localhost` — не пустит), порт
  5432, логин и пароль базы проекта. Из командной строки:
  `ssh -N -L 15432:127.0.0.1:5432 <логин>@<сервер>`, затем подключаться к `127.0.0.1:15432`.
  Пробросить можно только порт Postgres. Напрямую по IP сервера база недоступна.
- Django у себя на компьютере с базой сервера: туннель как выше, в `.env` —
  `DATABASE_URL=postgresql://<проект>:<пароль>@127.0.0.1:15432/<проект>`. Это рабочая
  база: `migrate` с вашего компьютера меняет продакшен.
- Копию базы — к себе: туннель как выше, затем
  `pg_dump -h 127.0.0.1 -p 15432 -U <проект> -Fc <проект> > <проект>.pgdump` и у себя
  `pg_restore --no-owner --no-acl -d <локальная база> <проект>.pgdump` (pg_dump/pg_restore 17+).
  В копии прода — персональные данные: держите её на зашифрованном диске и не пересылайте.
- Свежие данные прода в dev-проекте (проверить миграцию на настоящих данных) — попросите
  администратора: он заменит базу `<проект>_dev` копией прода одной командой (ADMIN.md).
- Поднимать свою базу в контейнере **нельзя**: её не будет в нормальных бэкапах.
  Нужна база, другой пользователь или расширение — к администратору.

**Тесты Django** создают базу `test_<проект>` — на сервере это не работает (создавать базы
пользователю проекта нельзя). Тесты гоняют в CI или локально.

**Тесты в CI (GitHub Actions).** Базу для тестов CI поднимает сам — временный контейнер
в блоке `services:` workflow, к базам сервера CI не подключается, настоящие пароли ему
не нужны. Чтобы «в CI зелёное» значило «на сервере заработает»:
- Тестовая база в CI — **не суперпользователь**, а владелец своей базы, как на сервере
  (создать отдельного пользователя с `CREATEDB` для тестовой базы). Иначе миграция
  с `CREATE EXTENSION` пройдёт в CI и упадёт при выкладке: на сервере расширения ставит
  администратор.
- **Версия Postgres — как на сервере** (сейчас 17). Сменится на
  серверах — поменять и в workflow.
- Тесты идут на **пустой базе**. Миграции, которые меняют данные, проверяйте на dev-проекте
  с копией данных прода, прежде чем выкладывать в прод.
- **Внешние сервисы** (почта, платёжки, чужие API) в тестах подменяйте заглушками:
  иначе тесты падают от чужих сбоев или шлют настоящие письма.
- Ограничения сервера, которых в CI нет: таймаут запроса и лимит подключений (ниже).

У пользователей базы есть лимит подключений, у Postgres — ещё таймаут запроса
(по умолчанию 60 секунд). Если миграциям или отчётам нужно больше — к администратору.


## Что происходит автоматически

- Каждую ночь: бэкап вашего проекта — файлы, Docker volumes, дамп базы.
- Каждое воскресенье: удаление неиспользуемых Docker-образов старше 7 дней
  (volumes и работающие контейнеры не затрагиваются).
- Сервер иногда перезагружается после обновлений (администратор предупредит).
  Сервисы с `restart: unless-stopped` поднимутся сами — он уже есть в `extends`.
  Сервис без `restart` после перезагрузки будет молча лежать.

доступ к Docker, смена IP, восстановление из бэкапа, исключения из «Правил для compose».
