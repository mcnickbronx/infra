# Первый сервер: памятка для новичков

Для тех, кто впервые арендует сервер. По шагам — от ключа на вашем компьютере до сайта с SSL,
бэкапами и уведомлениями. Займёт около часа. Подробности по каждому шагу — `ADMIN.md`.

Где выполнять команду, написано над ней: **у себя** — терминал вашего компьютера,
**на сервере** — после входа по SSH.

## Что понадобится

- Компьютер с терминалом: macOS, Linux или Windows 10/11 (PowerShell — `ssh` там уже есть).
- **Менеджер паролей** — Bitwarden, KeePassXC, 1Password или похожий. Туда пойдут копия ключа,
  пароль root от хостера, пароль бэкапов и ссылка доступа. Без него лучше не начинать.
- Деньги на VDS. Для нескольких небольших сайтов с базой хватает 2 CPU, 4 ГБ памяти и 40 ГБ диска.
- По желанию: домен, объектное хранилище S3 для копии бэкапов (стоит копейки), Telegram.

## 1. SSH-ключ — ваш пропуск на сервер

Ключ — пара файлов. **Закрытый** (`~/.ssh/id_ed25519`) остаётся у вас и никому не передаётся.
**Открытый** (`~/.ssh/id_ed25519.pub`) кладут на серверы — его показывать можно. Вход по паролю
движок выключает: на сервер попадает только тот, у кого есть закрытый ключ.

Уже есть ключ (`ls ~/.ssh/*.pub` что-то показывает) — новый не нужен. Нет — у себя:

```bash
ssh-keygen -t ed25519 -C "имя@ноутбук"
```

- Куда сохранить — Enter (по умолчанию).
- **Пароль ключа (passphrase) — задайте обязательно.** Закрытый ключ — обычный файл: он может
  уехать вместе с украденным ноутбуком, бэкапом или облачной папкой. С паролем такой файл
  бесполезен.
- Чтобы не вводить пароль ключа при каждом входе, его запоминает агент. macOS:
  `ssh-add --apple-use-keychain ~/.ssh/id_ed25519` — пароль ляжет в Связку ключей; чтобы так было
  и после перезагрузки, в начало `~/.ssh/config` — `Host *` и под ним строки `AddKeysToAgent yes`
  и `UseKeychain yes`. Linux — обычно
  спрашивает сам рабочий стол. Windows — включите службу «OpenSSH Authentication Agent» и выполните
  `ssh-add`.
- **Копию закрытого ключа** положите в менеджер паролей (вложением). Не пересылайте его
  в мессенджерах и почте, не кладите в git и облачные папки.
- Ещё надёжнее — ключ, который нельзя скопировать: Secretive на Mac (ключ в чипе) или YubiKey.
  Сервер такие ключи понимает.

Открытый ключ — его вы вставите у хостера:

```bash
cat ~/.ssh/id_ed25519.pub            # Windows: type $HOME\.ssh\id_ed25519.pub
```

Строка вида `ssh-ed25519 AAAA… имя@ноутбук` — копируйте её целиком.

## 2. Заказать VDS

- **Образ — Ubuntu 26.04 LTS**, чистый: без панелей (ISPmanager и т.п.) и готовых «приложений».
  24.04 тоже работает, но не желательно (README, «Ограничения»).
- **SSH-ключ — при заказе.** В панели хостера есть раздел «SSH-ключи»: добавьте туда строку
  из `.pub` и выберите этот ключ при создании сервера. Тогда root входит по ключу.
  Забыли — хостер пришлёт пароль root, и ключ можно положить самому (у себя; спросит этот пароль
  один раз):
  ```bash
  ssh-copy-id root@<IP>
  # Windows: type $HOME\.ssh\id_ed25519.pub | ssh root@<IP> "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
  ```
- **Пароль root — в менеджер паролей.** По SSH root скоро закроется, но пароль нужен для
  **консоли** в панели хостера (VNC, KVM, «Консоль»). Это запасной вход, если SSH закрылся:
  сменился IP, ошибка в настройках. Найдите консоль сразу, пока всё работает. Пароля нет —
  в панели обычно есть «Сбросить пароль root».
- Запишите **IP сервера**.

## 3. Ваш IP и вход с меняющегося адреса

SSH открыт только с ваших IP — остальной интернет до него не достучится. Свой IP: 2ip.ru
(или `curl ifconfig.me`). Его найдёт и `infra init` в следующем шаге — останется подтвердить.

Если IP меняется:

- **Домашний интернет, IP меняется время от времени** — впишите подсеть провайдера
  (`203.0.113.0/24`; её показывает whois вашего IP, например на 2ip.ru).
- **Мобильный интернет, поездки, чужой Wi-Fi — ссылка доступа.** Одна секретная ссылка
  на сервер: открыли её с телефона или ноутбука, нажали «Открыть SSH» — вашему текущему IP
  SSH открыт на сутки, в Telegram придёт сообщение. Войти по-прежнему можно только ключом:
  ссылка открывает лишь дверь, а не замок. Включена сама; получить её — после установки,
  на сервере:
  ```bash
  sudo infra-access link
  ```
  Ссылку — в менеджер паролей и передавайте как пароль. Утекла — перевыпустите (ADMIN.md,
  «Ссылка доступа»).
- **Заблокировали себя** — консоль хостера (шаг 2), дальше — ADMIN.md, «Если что-то сломалось».

## 4. Поставить движок

У себя: `ssh root@<IP>`. Затем на сервере:

```bash
git clone -q https://github.com/mcnickbronx/infra.git /opt/infra
git -C /opt/infra checkout -q v1.7.0          # последняя версия — CHANGELOG.md
/opt/infra/install.sh
infra init
```

`infra init` задаст четыре вопроса:

1. **Имя сервера** — латиницей и коротко, например `shop-1`: оно в уведомлениях и в папке бэкапов.
2. **Email для Let's Encrypt** — настоящий: туда пишут, если сертификат не продлевается.
3. **SSH-ключи** — найдёт тот, с которым вы вошли (его положил хостер). Подтвердите.
4. **Ваши IP** — найдёт текущий. Подтвердите или допишите подсеть (шаг 3).

На «Настроить сервер сейчас?» — `y`. Настройка идёт 5–10 минут.

Дальше вход — под `admin`, root по SSH закрыт. **Не закрывайте окно с root**, пока
не проверите вход в новом окне терминала (у себя):

```bash
ssh admin@<IP>
```

Пустило — можно закрывать старое. Удобно дать серверу короткое имя — у себя в `~/.ssh/config`:

```
Host shop-1
    HostName <IP>
    User admin
```

Теперь вход — `ssh shop-1`.

## 5. Пароль бэкапов — в менеджер паролей

Все бэкапы зашифрованы паролем restic. Он создаётся сам и лежит на сервере, но **если сервер
пропадёт, без этого пароля бэкапы не открыть — даже вам**. Заберите копию файла с паролями
к себе (пароли на экран не выводятся), у себя:

```bash
mkdir -p ~/infra-access && chmod 700 ~/infra-access
ssh shop-1 sudo cat /etc/infra/secrets.yml > ~/infra-access/shop-1.yml
chmod 600 ~/infra-access/shop-1.yml
```

Из этого файла `restic_password` — в менеджер паролей. Менять его нельзя: им зашифрованы
все копии.

## 6. Копия бэкапов в S3 — чтобы пережить потерю сервера

Бэкап на самом сервере спасает от ошибок (удалили файл, сломали базу), но не от пропажи сервера
или взлома. Для этого — копия в S3: сервер каждую ночь дописывает туда снимки и **не может их
стереть**.

1. В панели хостера — «Объектное хранилище» (S3), создайте приватный бакет. Можно у другого
   провайдера, чем сервер: так надёжнее. Проверено на Timeweb Cloud; подойдёт любой S3
   с версионированием и Object Lock.
2. В настройках бакета:
   - **версионирование** — включить;
   - **Object Lock** — включить, режим **COMPLIANCE**, срок **30 дней**. Часто его можно
     включить только при создании бакета — включайте сразу;
   - **жизненный цикл**: текущие версии — прятать через 45 дней, прежние версии — удалять
     через 31 день. Без этого бакет растёт бесконечно.

   Так даже тот, кто украл ключи сервера, 30 дней не сможет удалить копии.
3. Создайте **ключи доступа** к бакету (access key и secret key) и запишите **адрес хранилища**
   (endpoint) — его показывает панель, например `https://s3.example.ru`.
4. На сервере — ключи (откроется редактор, строки уже есть, пустые):
   ```bash
   sudo infra edit secrets      # s3_access_key: "..." и s3_secret_key: "..."
   ```
   Затем адрес бакета:
   ```bash
   sudo infra edit              # строка restic_s3_repository_base: "s3:https://s3.example.ru/<бакет>"
   ```
   После сохранения — «Применить?» → `y`.
5. Проверить, не дожидаясь ночи, — на сервере:
   ```bash
   sudo systemctl start backup          # бэкап сейчас, несколько минут
   sudo journalctl -u backup -n 50      # что получилось; ошибки — здесь
   sudo infra status                    # бэкап — сегодня, «копия в S3»
   ```

Третья копия — у вас на компьютере: раз в неделю
`tools/fetch-backups.sh shop-1` из этого репозитория (нужен `rsync`). Она дописывает только новые
файлы и ничего у вас не удаляет.

## 7. Уведомления в Telegram

Сервер сам пишет в Telegram — только о новых и прошедших проблемах (диск, память, упавший сайт,
сертификат, бэкап), а утром присылает сводку. **Нет утренней сводки — сервер лежит.**

1. В Telegram — [@BotFather](https://t.me/BotFather), команда `/newbot`, имя бота — получите токен.
2. Откройте своего бота и нажмите Start (или добавьте его в чат команды и напишите туда что-нибудь).
3. На сервере: `sudo infra edit secrets` — токен в `telegram_bot_token`.
4. `sudo infra-notify --find-chat` — покажет id чата; впишите его в `telegram_chat_id`
   (`sudo infra edit secrets`).
5. Проверка: `sudo infra-notify "проверка"` — сообщение пришло.

То же — в меню `sudo infra` → «Уведомления в Telegram». Telegram с сервера закрыт — прокси
в `telegram_proxy` (ADMIN.md, «Уведомления в Telegram»).

## 8. Домен и первый сайт

1. У регистратора домена — **A-запись** `example.ru` (и `www`, если нужен) → IP сервера.
   Начинает работать от нескольких минут до суток.
2. На сервере `sudo infra edit` — проект в `projects:`:
   ```yaml
   projects:
     site:
       net: 11            # номер сети: у каждого проекта свой, потом не менять
       db: postgres       # нужна база; без строки — без базы
       # devs: [anna]     # кто ещё работает с файлами (шаг 9)
   ```
   «Применить?» → `y`.
3. Код и `compose.yml` — в `/srv/projects/site/web`. Как написать `compose.yml`, чтобы сайт
   получил домен и SSL, — `TEAM.md`, там готовый шаблон. SSL выпустится сам.
4. Доступ к базе — в `.env` проекта (пароль на экран не выводится):
   `sudo project-db-env site`.
5. Запуск — `sudo project-compose site up -d`.

## 9. Люди: кто ещё заходит на сервер

Каждый человек присылает **свой открытый ключ** (шаг 1 — пусть сделает у себя, с паролем)
и свой IP. На сервере `sudo infra edit`:

```yaml
people:
  anna:
    key: "ssh-ed25519 AAAA... anna@laptop"
    ips: [198.51.100.23]      # с меняющимся IP — подсеть или ссылка доступа (шаг 3)
```

и `anna` — в `devs:` нужных проектов. Человек заходит по SSH/SFTP и видит только папки своих
проектов. Ушёл — убрать из `server.yml`: аккаунт, ключ и IP исчезнут сами. Что отдать
человеку — `TEAM.md`.

**Docker (`docker_users`) — только тем, кому доверили бы root:** кто запускает контейнеры,
тот фактически администратор сервера.

## 10. Какие ещё есть настройки

Всё — в `/etc/infra/server.yml` (`sudo infra edit`). Полный пример с пояснениями —
`/opt/infra/server.yml.example`, оттуда удобно копировать блоки. Ключи — в `secrets.yml`
(`sudo infra edit secrets`).

| Что | Где и как |
|---|---|
| Ваши ключи и IP | `admin_keys`, `admin_ips` |
| Люди | `people:` — `key`, `ips` |
| Кто запускает контейнеры | `docker_users` |
| Проект | в `projects:` — `net` (обязательно), `db: postgres`, `devs`, `domains` (для справки) |
| Лимиты проекта | `memory: 4g`, `cpus: 2` (по умолчанию 2g и половина CPU сервера) |
| База проекта | `db_conn_limit` (50), `db_statement_timeout` (60s) |
| Автовыкладка | `autodeploy: true` у проекта, `ghcr_user` и `ghcr_token` в `secrets.yml` (ADMIN.md) |
| Частые бэкапы | `backup_hourly: db` или `all` у проекта, `backup_every`: 1, 5, 15, 30 или 60 минут |
| Копия в S3 | `restic_s3_repository_base`, ключи `s3_access_key`, `s3_secret_key` (шаг 6) |
| Telegram | `telegram_bot_token`, `telegram_chat_id`, `telegram_proxy` в `secrets.yml` (шаг 7) |
| Пороги уведомлений | `disk_alert_percent` (80), `memory_alert_percent` (10), `notify_summary_time` ("09:00") |
| Ссылка доступа | `access_link: false` — выключить, `access_link_hours` (24, до 72), `access_link_host` — свой домен вместо sslip.io |
| Часовой пояс | `timezone` (Europe/Moscow) |
| Лимиты запросов к сайтам | `traefik_ratelimit_average` (200 в секунду), `traefik_inflight_max` (150) |
| Ubuntu 24.04 | `ubuntu_version: "24.04"` |

Любое умолчание движка (`/opt/infra/group_vars/all/main.yml`) можно поменять так же — строкой
в `server.yml`. Ключ с опечаткой движок не примет: проверка остановит `apply` до изменений.

## 11. Дальше — регулярно

- **Раз в неделю:** `sudo infra update` (или меню → «Обновления») — Docker, Postgres, Traefik,
  пакеты. Новое ядро — сервер перезагрузится сам, сайты лягут на минуту: делайте вечером.
  Забудете — напомнит Telegram.
- **Раз в неделю:** `tools/fetch-backups.sh shop-1` — копия бэкапов к вам (шаг 6).
- **По уведомлениям:** что делать — написано в самом сообщении.
- Обновления безопасности Ubuntu ставятся каждую ночь сами.

## Чего не делать

- Не пересылайте закрытый ключ (`id_ed25519` без `.pub`) и `secrets.yml` в мессенджерах,
  почте, git.
- Не храните пароли и `.env` в git-репозиториях проектов.
- Не меняйте пароль restic — им зашифрованы все бэкапы.
- Не открывайте порты в файрволе «на всякий случай» и не убирайте белый список SSH.
- Не запускайте сайты мимо проектов (`docker run` руками): у них не будет лимитов, своей сети
  и бэкапа.

## Если что-то пошло не так

- **Не пускает по SSH** — консоль хостера, вход root с паролем, затем
  `ufw allow from <ваш IP> to any port 22 proto tcp comment ansible-wl`
  и свой IP — в `admin_ips` (иначе следующий `apply` правило уберёт).
- **Сайт не открывается** — A-запись уже ведёт на сервер? Затем на сервере
  `sudo project-compose <проект> ps` и `sudo project-compose <проект> logs --tail 50`.
- **`apply` остановился с ошибкой** — читайте строку `fatal:`: там по-русски, что поправить.
  Проверки настроек останавливают прогон до любых изменений.
- **Что вообще с сервером** — `sudo infra status`.
- Вопрос или ошибка в движке — issues на GitHub.
